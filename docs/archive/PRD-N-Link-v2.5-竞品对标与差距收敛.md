## 一、背景与目标

### 1.1 为什么现在做这一版

三件事同时发生，逼着这版必须从「加功能」切回「把稳做穿 + 补齐专业面」：

1. **官方开始抢第三方卖点。**【官】尼康影速传 NX MobileAir「自 1.6.0 起 Android 专业版解除对相册和保存文件的功能限制，现可免费下载使用」；同时 **Nikon IMAGE SPACE / 影像馆 2026-10-15 终止服务**，云端备份路径消失。用户会开始问「官方都免费了，我为什么还要装你」。
2. **同赛道竞品正在从「传图工具」升级为「遥控工作台」。**【实】ZRelay 3.0 加了光圈/ISO/WB/快门/实时取景；【实】开源的帧澈 ZENCHE 已把「可调帧率 + `.cube` LUT + RGB 波形 + 矢量示波器 + 峰值对焦 + 斑马纹 + 包围/焦点包围 + RAW+JPEG 配对 + 107 款云创预设近似监看」写进 README。我们的功能表在这一层**逐项落后**，而这三项恰好是「专业感」的来源。
3. **我们自己的「稳」从来没有被证明过。** 用户高频痛点榜第一位至今仍是「STA/热点连不上或搜不到相机」（09-08、09-11、09-15、09-16、09-17 三次），09-17 甚至因一次回归要求整体回退 v2.0.1。而仓库现状是：**无任何量化基线**（漏斗只存内存 12 次）、**无 CI**、**无 instrumented 测试**、**核心连接状态机零单测**、兼容矩阵 **9/13 条从未真机验证**、崩溃只本地落盘。发版速度全场第一（6 周 15 版），可证明的稳定为零。

### 1.2 本期目标（三条，可验收）

| 目标 | 内容 | 度量 |
|---|---|---|
| **T1 建立可信基线** | 连接漏斗与关键指标可导出、可统计，先有数再谈优化 | 每次连接产出 1 条结构化漏斗记录（Stage/Reason/耗时/通道/机型/固件），可在设置页一键复制、可导出的 CSV；崩溃与 ANR 可选上报（须用户同意） |
| **T2 收敛地基债** | 消灭 9 条 GAP 地基债里 P0 的 6 条 | STA 首连成功率、p95 连接耗时、1000 张相册首屏时间、>2GB 传输正确性、事件不丢失 —— 见 §6 指标表 |
| **T3 补齐专业面（监看 + 拍摄）** | 监看帧率自适应 + LUT/RGB 直方图/斑马纹/峰值对焦；包围曝光与焦点包围；RAW+JPEG 配对下载 | 监看 24–30fps（5GHz）；监看工具首屏可见；风光/产品两类场景端到端跑通真机 |

### 1.3 非目标（本期明确不做，避免重复提案）

| 不做 | 原因 |
|---|---|
| iOS 版本 | 结构性不可行：尼康无移动 SDK，**帧澈在 iOS 上同样做不到直连尼康 USB/PTP，只能靠 Mac 桥接**（其 README 自述）。我们主动选窄 Android 单端是正确决策，不回头。 |
| 多品牌（佳能/索尼/富士） | 影犀/帧澈的广度是它们的天花板：每品牌只能做 PTP 公共子集。单品牌深耕 + 私有语义吃干才是我们的位置。**索尼实时取景连帧澈都标「不支持」。** |
| 独立「下载管理页」 | 已否决并取消：本地照片页即已下载集合，重复建设（v1.2.1 已拍板）。 |
| 破解 LsSec / 反射隐藏 API / 接 libgphoto2/libusb / 引 OkHttp / 迁 Compose | 已否决（v2.2 §10、v2.3 决策）。 |
| 照抄影犀 40 个 `.cube` | **版权不可用**（Color Grading Central / Denver Riddle）。LUT 只能自制或用无版权授权包。 |
| 伪造尼康官方 App 的 initiator GUID「蹭已配对状态」（aero-shutter 做法） | 合规与信任风险，不做。 |
| 快门次数「现拍一张兜底」 | 会让用户快门数 +1，隐私底线，不做（v2.4 已拍板）。 |
| AI 修图 / 云创预设商店 | 既有独立 PRD（`PRD-N-Link-AI修图.md`，仍 Draft），不并入本期，避免同时动两块核心区。 |

## 三、竞品对比结论（决定优先级的 9 条）

> 完整矩阵与逐家档案见分析文档 §3/§2，这里只留能改变排期的结论。

1. **没有任何一个竞品同时具备三通道。**【实】ZDROP 无蓝牙、ZRelay 无 USB、帧澈无 BLE 配对、SnapBridge 无 USB、影速传无 WiFi 遥控。**「三通道全量 + 统一诊断」是我们的结构性位置，本期不是要加新通道，而是要把三通道每一条都做到「可解释的成功率」。**
2. **尼康 BLE 配对协议 + Blowfish 是全场（含开源）唯一实现** → 这是我们的护城河，也是「为什么我们能做到免手工输密码」的解释权。**别把它当作已完成的资产：`0x2006` 写时间、`0x2007` 写位置至今只是 UUID 声明、零读写**（GAP-17），SnapBridge 已做到，我们差一半。
3. **官方免费化改变了卖点排序**：「传原图」不再是差异点，**「机身上没有的那三件事」（有线之外的遥控参数面 + 监看影调工具 + 断线自愈）才是**。这直接决定了 T3 的内容。
4. **监看工具是专业感的第一来源，也是我们最大的空白。** 帧澈（开源、免费）与影控台（¥148 买断）都给了 LUT + 波形 + 峰值 + 斑马 + 可调帧率。我们只有亮度直方图 + 15fps + CPU 解码。**这项不补，功能表层面我们输给一个已停更 29 天的开源项目。**
5. **兼容治理必须当产品资产运营。** ZRelay 把规则放服务端下发（`/v1/camera-rules`）做到不发版修兼容；我们已经把规则数据化到 `rom_rules.json`（v2.2 G11）但**没有热更新通道、且 9/13 条从未真机验证**。**差距不在架构，在于有没有把「验证」当日常。**
6. **传输工程对手已给出可验证的基线**：ZDROP 双 data 通道、aero-shutter 4MiB 分块 + TCP 窗口调优、ZTransfer 声称 `0x9A6C GetPartialObjectHighSpeed` 可用。**我们的分块已是 4MB（`TransferManager.kt:78`），但队列并发度 1、`offset: Int`、数据期不抽 event —— 三条都是速率与正确性的天花板**（GAP-03/04/05）。
7. **私有命令码存在待核验冲突**（GAP-25）：ZTransfer 明确写「0x952B 等旧值是错的」，主张 `0x9838/0x93D4`。**我们的 `0x952B/0x935A` 来自 ZDROP 反汇编且已真机跑通 STA 主机注册**，因此更可能是**两条并存通路**（WMA 主机注册 vs 无线连接计算机）而非谁错 —— 但在探测完成前，**任何文档与对外文案都不得写成「唯一正确路径」**。这是必须先做的研究项，不是功能项。
8. **发版速度我们第一，可证明的稳定为零** → 本期最重要的一个动作不是加功能，是**先把基线建起来**（FR-01），否则每一条「优化」都无法向群里证明。
9. **可信性基建有洞，且洞很显眼**：无 LICENSE（对外称「开源」但无授权文件）、README 引用两个不存在的文档（死链）、`proguard-rules.pro:4` keep 了一个不存在的包（规则失效）、`NikonLink` 重名且对方握有 GitHub 重定向权重。**这些是半天到两天的工作量，收益是「可信」本身。**

## 五、功能需求与预期效果

> 每条需求统一结构：**问题证据 → 需求（规则化）→ 文案要求 → 闸门与回退 → 验收标准 → 预期效果**。
> 闸门命名沿用既有前缀习惯：连接类 `conn25_*`、传输类 `xfer25_*`、监看类 `lv25_*`、拍摄类 `shot25_*`。**所有闸门默认值与 v2.3.1 行为一致，关掉即逐像素/逐行为回到旧版**（沿用 v2.2/v2.3 已确立的可回退裁定）。

### A0 · FR-01 连接与传输指标基线

- **问题证据**【实】`ConnFunnel` 仅内存保留 12 次、无聚合；崩溃仅落 `crash.log`（`AppEventLogger.kt:104-116`）；全仓无 `p50/p95` 相关代码（v2.2 §10.4 自述「8 项指标未知」）。**结果：「连不上」到底影响 3% 还是 30% 的用户，我们答不上来。**
- **需求**
  1. 每次连接尝试落一条**结构化记录**（本地 Room 或 JSONL）：`ts / 通道(AP/STA/USB) / 机型 / ROM 家族 / Android API / 相机型号 / 相机固件 / 各 Stage 耗时 / 终态 / Reason 码 / 重试次数 / 是否 BLE 参与`。
  2. 设置页「连接诊断」新增**近 7 天汇总视图**：三通道各自首连成功率、p50/p95 连接耗时、Top 5 失败原因码、失败机型 Top 5。
  3. 「一键复制诊断」扩展为**带结构化附件的反馈包**（漏斗 + 汇总 + 最近 200 行事件日志），可直接发到 QQ 群。
  4. 传输侧同口径落记录：`文件数/总字节/用时/平均速率/重试次数/续传次数/失败原因`。

- **验收**：四角与中心 5 点标定误差 ≤画面短边 2%；标定表进入数据资产（不发版可新增）。
- **预期效果**：点哪对哪「看得见」；同时把两处「参考竞品约值」的技术债清零。

### B6 · FR-14 私有命令码探测专项（研究项，产出结论而非功能）

- **问题证据**：①【网/实】ZTransfer 主张 GetPairingCode `0x9838` / ConfirmPairing `0x93D4`，并称「`0x9010/0x9435/0x935A/0x952B/0x9431/0x9400` 全部是错的」，另称 `0x9A6C GetPartialObjectHighSpeed`、`0x9918 GetPartialObjectEx` 可高速取局部对象。但其源码注释把这套码限定在 **Nikon「Connect to computer」模式**，而我们的 `0x952B/0x935A` 服务于 **SnapBridge 系 WMA 主机注册**（`zdrop_hostreg_disasm.txt` 取证）且真机可用 → **两条通路并存的可能性远大于谁对谁错**。②【实】**我们代码里只有 `OP_NIKON_CHECK_EVENT = 0x90C7`（`PtpProtocol.kt:96`），全仓无 `0x9714`（GetEventEx）**，而 `PtpSessionManager.kt:321-322` 的注释却把它写成「Nikon GetEventEx (0x90C7)」——**命名与注释自相矛盾，且我们可能从未真正取回过事件体**（与 FR-04 同根同链）。
- **需求**：用 `tools/ptp_probe.py` + 真机做一轮**只读能力探测**（`FuncSummary`/`OFCs` 列举 + 逐 op 响应码记录），产出：① 各机身实际支持的厂商 op 清单；② **`0x90C7`(CheckEvent) 与 `0x9714`(GetEventEx) 的语义分工**，据此修正常量命名与注释（**纯改名改注释，不改行为**）；③ `0x9A6C` / `0x9918` 是否存在与可用；④ `0x9838/0x93D4` 与 `0x952B/0x935A` 的模式归属（各在哪种机身连接模式下有效）；⑤ 结论写回 `docs/`，并**同步修正 README 与本文档措辞**。
- **验收**：≥3 款机身（Z8/Z6III/Z50II）+ ≥2 固件版本的探测记录归档；探测脚本**只读、不改机身状态**（不得让快门 +1）。
- **预期效果**：**若 `0x9A6C` 成立，下载速率可能出现全场唯一的一次跃升**（见分析文档 §8 机会 6）；若 GetEventEx 确认为「此前只查不取」，FR-04 的收益将显著放大；若都不成立，也把「我们用的是错的」这个潜在口碑风险提前拆除。**本条不承诺功能，只承诺结论。**

### B7 · FR-15 兼容矩阵运营（把「验证」当日常）

- **问题证据**【实】`assets/compat/rom_rules.json` 6 家族 19 条，**13 个 `lastVerified` 中 9 个为 null**；预检面板只有文案、无「去设置」深链落点；v2.2 G21（热更新）未做。ZRelay 已在用服务端下发。
- **需求**：① 9 条未验证条目按真机排期回填（依赖 FR-01 的机型分布数据决定优先级）；② 预检每条给「去设置」深链（Settings Intent 可达的直达，不可达的给「复制路径 + 截图指引」）；③ **只读**兼容规则热更新通道（拉取 JSON → 校验 schema 与签名 → 落本地缓存，失败静默用内置版本）；④ 新增**机身侧**矩阵 `camera_rules.json`（机型×固件×通道能力，供 FR-05/11/13 消费）。

## 八、范围铁律、风险与回退

### 8.1 范围铁律（沿用既有裁定，逐条生效）

1. **不做顺手重构**：本期只允许动 §四 表中列出的文件；`PtpSessionManager` / `TransferManager` 串行队列 / `ConnectionStateMachine` 三处为 A 禁区，**只有 FR-04/05/06 三条以闸门 + 最小增量方式豁免**（各 ≤80~120 行，只加不改语义）。
2. **已跑通的功能不得回退**：v2.0.1 的 STA 连接、v1.3.0 的逐张入册、v1.2.1 的「不重复下载」与剩余进度、v2.2 的重试预算与预检 —— 全部列为**回归红线**，验收必须逐条复测。
3. **一切新行为可回退**：`conn25_* / xfer25_* / lv25_* / shot25_*` 闸门 + 「经典外观/降低透明度」两个既有开关永久保留。
4. **文案说人话**：失败提示不含秒数（避免闪烁）、不出现术语、长指引进可换行卡片、更新弹窗纯文本 ≤500 字。
5. **隐私底线**：不让快门 +1 换取数据；不默认上传任何用户照片；云端/崩溃上报必须显式同意；诊断导出只含设备与错误信息，不含文件内容。
6. **法律边界**：竞品结论仅来自 APK 静态分析（公开分发物的结构与字符串），不复制任何竞品代码；私有命令一律写「实测观察」不写「厂商规范」；对外协议表述为「基于 ISO 15740 / CIPA DC-005-2005 自研实现」+ 商标免责声明；**影犀 40 个 `.cube` 有版权，禁止照抄**；ZTransfer **无 License，禁止引用其任何代码/常量数值**（其 op 码须由我们自行探测得出）。

### 8.2 风险登记

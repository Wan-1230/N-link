## 3. 横切根因

- **RC-A（主因）WLAN 层反复闪断**`已验证`：掉线发生在「持有请求在册且 bound」的 R1/R3（L70/L193-199），且该机相机热点的 caps 是 `validated=true internet=true`（L69/L192）——即 FR-33 的「未验证网络被 ConnectivityService 回收」机制**在这台机器上不成立**（默认请求本就匹配，持有也在）。本轮失败是另一种机制：OEM WLAN 策略（与「WLAN 始终开启」开关相关，但本轮开关时序与成败不完全对齐，见 §8）或相机侧 AP 复位（R1/R2 中 event_read_error 先于 wlan0 消失 0.2–1.2s，L101→L104、L146→L149）。`推断待验证`
- **RC-B 蜂窝 lane 30s 超时空转**`已验证`：R5 三次 30s 级超时 ≈73s、R2 恢复轮一次 30.0s（L177）。ZDROP 套接字超时为 6000ms（其日志 L345「after 6000ms」）。TCP 到在线相机实测 <1.5s，30s 只在黑洞 lane 上纯亏。
- **RC-C 窗口/状态陈旧**`已验证`：net_req 4s 窗口三次错过回连（L118/L169/L227）；ap_ctx/ap_gateway 在 wlan0 下落过程中仍报 true/stable（L219/L221），把轮次推进到蜂窝 lane。
- **RC-D 会话空闲无保活**`推断待验证`：R1 建立后命令通道 14s 无任何流量（L79-80 之后无 ptp_tx），随后 event_read_error。本方 CheckEvent 仅在 OpenSession 后排空一次（PtpSessionManager.kt:423），无周期心跳；ZDROP 有 `keepAlive=true` + heartbeat（其日志 L334「heartbeat failure … count=1」）。
- **RC-E 自动重连被自家 cooldown 吞掉**`已验证`：L215。reconnect_trigger 恰好落在 WLAN 即将回连的窗口，等 1s 后被判 fallback_cooldown，整轮记 superseded。

## 4. ZDROP 日志策略提炼（同机同相机）

| 环节 | ZDROP（当前会话 L18-L64） | 本方现状（本轮日志） |
|---|---|---|
| 入口 | 点「连接」前用户已在热点上；tap→cleanup 旧传输 5ms（L19-24） | 需先「扫描相机」填候选列表，否则弹手动 IP 框（DashboardFragment.kt:1122-1130） |
| endpoint | **硬编码默认 192.168.1.1:15740，零扫描**（L29；dex 证据见 §5） | 网关学习 1200+700ms 双采样 + TCP 筛探 + 400ms settle = DISCOVER p50 2335ms |
| 绑网 | `bind requested timeout=8000 target=default`，onAvailable +7ms（L30-32）；显式 socketFactory 绑网（L34） | net_req 4s 窗口，错过回连即 unregister |
| 就绪等待 | 固定 1200ms + gateway/local 双值一致判 stable（L33） | 1200+700ms 双采样 |
| 握手 | 双通道一次过：cmd socket +174ms、init ack +162ms、event ack +403ms、open-session +178ms、DeviceInfo +381ms；tap→complete **2.75s**（L36-52） | 握手 6–152ms 不弱，但被 DISCOVER/ROUTE/蜂窝超时拖累 |
| 重试 | 每轮 2 次 attempt，INIT_EVENT 失败 delay=7000ms 重试（旧会话 L181）；UI 点击 cooldown ~1s（L254） | MAX_ATTEMPTS=10 + 退避表；INIT_EVENT 7s 冷重试已有（FR-31②） |
| 保活 | 前台服务 dataSync|connectedDevice + partial wake lock + **Wi-Fi lock lowLatency** 于握手前获取（L39-41）；keepAlive heartbeat + 3 次 recovery（L334-378） | ConnectionService 有；WifiLock HIGH_PERF 有；**无命令通道心跳** |
| 吞吐 | receiveBuffer=3461120（3.3MB）；6.29MB/2421ms（L43/L68） | 未调接收缓冲 |
| 诊断 | 每轮带 radio=2437MHz/ch6/54Mbps/-39dBm（L34） | sta_ifaces 有，radio 信息无 |

ZDROP 在同机也会失败（旧会话两次 INIT_EVENT Connection reset、一次会话期 socket failure→onLost→recovery 耗尽），但其**单轮成本 2.75s、重试间隔 7s、UI 可 1s 后再点**，失败代价小；本方单轮成本 10–84s，失败一次就分钟级。

## 5. ZDROP APK 方法级逆向证据（classes.dex，dexdump -d）

1. **原生 WLAN 面板拉起**（截图一的底部面板）：方法 `o1` 内
   `1ca87a` 取 Application → `1ca882` new Intent → `1ca886` const-string `"android.settings.panel.action.WIFI"`（= `Settings.Panel.ACTION_WIFI`，Android 10+ 标准化「设置面板」action）→ `1ca890` `const/high16 #268435456`（FLAG_ACTIVITY_NEW_TASK）→ `1ca89c` `Context.startActivity`。
   该 action 由系统设置以**应用内底部面板**形式渲染（AOSP 切片面板），不进入任何 OEM 深度链接的全设置页 —— 这就是「绕过 OriginOS/ColorOS 定制页」的实现：不是调底层私有 API，而是用各家 ROM 都必须实现的标准化 panel entry。`已验证`
2. **免扫描 endpoint**：状态类 `<init>` `1c42aa` 默认 host=`"192.168.1.1"`（SharedPreferences 键 `host`/`registered` 可覆盖）；方法 `m` 内网关解析链：`getLinkProperties(network).getRoutes()`（366477/366481 行）→ 若网关不可用「AP gateway unavailable; retaining entered host=」（`1a1499`）→ 若解析结果等于手机自身地址「AP target is handset address=…; using canonical fallback=192.168.1.1」（`1a1502`→`1a151a` 写回字段）。**全程无 mDNS/子网扫描/NSD**。`已验证`
3. **负证据**：全 dex `WifiNetworkSpecifier` / `addNetworkSuggestions` / `NetworkSuggestion` 匹配数 **0** —— ZDROP 不做免确认自动连网，AP 加入完全靠用户在面板里点 SSID。`已验证`
4. 保活字符串：`partial wake lock acquired`（293019）、`Wi-Fi lock acquired mode=`（293047）、`heartbeat failure transport=`（373560）、`keepAlive=`（419315）。`已验证`
5. 射频诊断：`WifiInfo.getFrequency/getLinkSpeed/getRssi`（367241-367279）。`已验证`

截图二（系统「互联网」整页）判读：面板左下「设置」按钮的跳转目标，属 AOSP 面板的预期出口；默认路径（面板内点 SSID→「完成」）不离开本应用。`推断待验证`（无法从截图单独证明点击来源）

## 6. 优化方案（全部闸门化，关闸=现行为；只动 AP/连接编排，不碰 STA 注册与 USB）

### P0 本轮落地候选
1. **AP 一键连接（省扫描）**：`DashboardFragment.connectForCurrentMode()` 的 WIFI_AP 分支改为：无候选时不再弹手动 IP 框——
   - 已在相机热点（`ApGatewayResolver.isOnCameraAp()`）→ 直接起轮次，endpoint=网关 ?: 上次配对 host ?: `192.168.1.1`（复用现成 resolve，仅 UI 层改道）；
   - 不在 → 先拉起 WLAN 面板（新 `ApWifiPanelLauncher`：`Intent("android.settings.panel.action.WIFI")`+NEW_TASK；API<29 回退 `ACTION_WIFI_SETTINGS`），置 `pendingAutoConnect`；现有全局 WiFi 回调（`WifiManager.networkAvailable` / wifi_sta network_restored）+ SSID 命中相机热点 → 自动起轮次。
   收益：操作步骤 3→1；与 ZDROP 截图流程同构。
2. **网关快路径**：`ApGatewayResolver.resolve()` 中 `isOnCameraAp() && 首采样有效` → 直接返回（跳过 RESAMPLE_MS 700 + TCP 筛探 800 + settle 400）。DISCOVER 2335ms→~1200ms，与 ZDROP 对齐。
3. **分 lane 套接字超时**：`PtpSessionManager.CONNECT_TIMEOUT_MS` 30000 → 非绑网 lane（fallback/蜂窝）8000，绑网 lane 保持。R5 的 73s 空转→≤24s，R2 恢复轮 30s→8s。
4. **会话级持有请求**：`StaNetworkRequester` 的 local-only 请求生命周期从「3–4s 窗口」改为「轮次开始注册 → 会话结束/WLAN 丢失宽限期注销」，并在 network_restored 时补注册。消掉 RC-C 的三次窗口错过。
5. **WLAN 新鲜度闸**：起 socket 前要求 2s 内 sta_ifaces 含 wlan0（或 WifiInfo supplicantState=COMPLETED 且 LinkProperties 非空）；陈旧则等 WLAN（≤8s deadline）而非向蜂窝发 30s socket。消掉 R5 的 ap_ctx 陈旧推进。
6. **空闲心跳**：established 后命令通道空闲 >5s 发一次 GetDeviceInfo(0x1001)（对齐 ZDROP keepAlive）；失败即触发现有恢复轮。验证 RC-D。

### P1 诊断

### P2 待拍板

9. 接收缓冲 3.3MB 与 radio 诊断字段（传输链路，另轮）。

## 7. 验证与回归
- 真机矩阵：开关 开/关 × 各 3 轮一键连接；判据：WLAN 在位时 tap→READY p50 ≤3s；蜂窝 lane 无 >8s 的 socket_try；面板拉起成功率；pendingAutoConnect 在面板点 SSID 后 ≤2s 起轮。

## 8. 未决分叉与判别实验
- 分叉：RC-A 是 OEM WLAN 策略 vs 相机 AP 复位。判别：P1 的 deauth 原因码（本地原因=手机侧；3/8 等=AP 侧踢）+ 掉线瞬间相机屏幕录像。

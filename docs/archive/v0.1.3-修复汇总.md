## T1 `fix-album-download-dedup` —— 下载重复

**改动文件**
- `camera/gallery/TransferManager.kt`
- `shared/data/NLinkDatabase.kt`

**核心修复**：`processQueue()` 的 `repeat(2)` 重试循环没有成功终止条件，首轮成功后又跑第二轮，而首轮成功已删除临时文件，第二轮完整重下并二次写入 MediaStore → 产生 `xxx (1).JPG`。**网络正常时每张照片也必然下载落盘两次**。改为仅失败时重试一次。

**其余改动**
- 入队去重：队列内同 handle + 已传输批量查询（400 一批，一次入队 1~2 次查询，取代 N 次 IO）
- `queueMutex` 保护 `transferQueue`/`currentTask`/`currentJob`/`isPaused`，消除主线程与协程线程竞态
- `transfer_history.file_handle` 唯一索引 + `Migration(1,2)`（备份表 `transfer_history_bak_1` → 去重 → 建索引，失败有清表兑底）
- DAO 获取改用 Hilt `NLinkDatabaseEntryPoint`（`TransferManager` 由 AppModule 手动 new，无法追加构造参数）

**自测结论**

| AC | 场景 | 结论 |
| --- | --- | :-: |
| AC-1 | 全选 50 张下载一次，无 `(1)` 副本 | ⚠️ 需真机。代码保证：成功不再重试，`downloadVia` 只落盘一次 |
| AC-2 | 连点下载 5 次不膨胀 | ✅ 入队阶段被队列内 handle 拦掉 |
| AC-3 | 已下载再全选不入队 | ✅ 已传输 handle 不入队，`download_start` 不打点 |
| AC-4 | 中途断连重试 1 次 | ⚠️ 需真机 |
| AC-5 | 切 Tab/退后台不并发重复 | ⚠️ 需真机。Mutex 保证无并发 |
| AC-6 | 日志中 `download_start` ≤ `download_done` | ✅ 成功路径各 1 条 |

**回退点**：L1 去掉 `AppModule` 的 `.addMigrations(...)` 并把 `version` 退回 1（去重退化为应用层 `EXISTS` 查询，功能无损）；L2 整分支回滚。

## T2 `fix-album-auto-refresh-on-connect` —— 连接后相册刷新

**改动文件**
- `camera/gallery/TransferViewModel.kt`
- `camera/gallery/TransferFragment.kt`

**核心修复**：`MainActivity` 四 Fragment 常驻、切 Tab 只 `hide()/show()`，故 `TransferFragment.onViewCreated` 的 `fetchPhotos()` **整个 App 生命周期只跑一次**（冷启动、相机未连）。`TransferViewModel` 已暴露 `connectionState` 但 Fragment 从未 collect。

**改动**
- `cameraReady = combine(connectionState, usbState)`：三个来源都必须覆盖 —— `FULLY_CONNECTED`、`BLE_CONNECTED`、**`UsbConnectionState.CONNECTED`**（USB 通道不进连接状态机，`ConnectionManager:535` 只打日志，纯 USB 场景必须单独判定）
- `stateIn(..., Eagerly, ...)`：冷启动即拿初值，满足"已连相机时冷启动也自动加载"

- `loadPhotos(force)` 守卫：`AtomicBoolean` + `loadJob.cancel()`；手动刷新走 `force = true` 保证永远可打断
- `downloadAll()` 数据源由 `_photoList` 改为 `filteredPhotos`，与 `selectAllFiltered()` 口径一致（原会把视频也拉进下载队列）
- **手动刷新入口完全保留**：`btnRefresh` 与下拉刷新行为不变

**自测结论**

| AC | 场景 | 结论 |
| --- | :-: |
| AC-1 | 冷启动 → 连相机 → 切相册，自动加载 | ⚠️ 需真机 |

## T3 `fix-shutter-aperture-control` —— 快门方向与光圈限位

**改动文件**
- `camera/params/CameraParameterManager.kt`
- `camera/params/CameraParamsViewModel.kt`
- `camera/liveview/LiveViewFragment.kt`
- `capture/RemoteFragment.kt`

**核心修复一（快门方向）**：滚轮把 `PROP_EXPOSURE_TIME` 的 raw 值（单位 **1/10000 秒**）直接当分母显示 —— `raw 40` 显示成 `1/40 s`，实为 **1/250s**。于是 raw 升序（变慢）与显示序列（1/10 → 1/4000，读起来变快）**方向完全相反**。附带导致 `indexOfFirst { it == current }` 恒匹配失败，滚轮每次跳回首项。

**核心修复二（光圈）**：`readLensInfo()` 其实**已经读到**镜头光圈上下限（`0xD0E5`/`0xD0E6`），但拼进 `lensName` 展示字符串后就丢弃了，`CameraInfo` 无任何结构化字段；`setAperture()` 也无 clamp 与回读校验。

**改动**
- 档位表收敛为 `ShutterCatalog` / `ApertureCatalog` 唯一真源，消除 LiveViewFragment / RemoteFragment / Manager **三处硬编码重复**
- `formatShutter()` 统一换算；`readShutterSpeed()` 复用同一函数，口径一致
- `resolvePickerIndex()` 改用 **raw 值**定位
- `CameraInfo` 增加 5 个镜头结构化字段；`apertureOptions()` 按当前焦距线性插值生成档位
- `setAperture()` clamp 到最近合法档 + 写入后回读比对；`setShutterSpeed()` 加 `coerceIn`
- 按 PRD Q3 决定：当前焦距**只在打开光圈滚轮时读一次**，不进 2 秒轮询

**自测结论**

| AC | 场景 | 结论 |
| :-: | --- | :-: |
| AC-1 | 刻度显示正确物理值 | ✅ 验算：`raw 10 → 1/1000`、`raw 40 → 1/250`、`raw 4000 → 1/2.5`（见下方口径说明，已按用户拍板调整） |
| AC-2 | 滚轮定位到当前值 | ✅ `raw 40` 精确定位 index 6 |
| AC-3 | 调节方向正确 | ⚠️ 需真机（逻辑已验证：`direction>0 → index+1 → raw 增大 → 曝光变长`） |
| AC-4 | 首尾限位 | ✅ `stepIndex.coerceIn` + `setShutterSpeed.coerceIn(10, 4000)` |
| AC-5 | 定焦 f/1.8 档位生成 | ✅ 验算得 `[1.8, 2, 2.8, 3.5, 4, 5.6, 8, 11, 16, 22]`，无 f/1.4 |
| AC-6 | 变焦 24-70 f/2.8-4 两端 | ⚠️ 需真机（插值验算 24mm→f/2.8、47mm→f/3.5、70mm→f/4.0） |
| AC-7 | 越界 clamp | ⚠️ 需真机（验算 `f/1.4 → f/1.8`） |
| AC-8 | 镜头未知回退 | ✅ 回退 f/1.4–f/22 通用 11 档 |
| AC-9 | 参数锁定 | ✅ 锁定即 `return false` |
| AC-10 | 两处口径一致 | ✅ 同源于 ViewModel |

**✅ 显示口径（原 PRD 内部矛盾，已由用户拍板）**

以 **1 秒** 为界，与 Nikon 机身一致：**不足 1 秒显示分数，1 秒及以上直接显示秒数**。

| raw | 曝光时间 | 显示 |
| --- | --- | --- |
| `40` | 1/250s | `1/250` |
| `2500` | 1/4s | `1/4` |
| `4000` | 1/2.5s | `1/2.5` |
| `10000` | 1s | `1s` |
| `13000` | 1.3s | `1.3s` |
| `300000` | 30s | `30s` |

分母精度分两档：≥10 取整（`1/769.2` 这类读数没有意义），<10 保留一位小数
——`0.4s` 的真值是 `1/2.5`，若四舍五入成 `1/3` 会偏差 20%，App 显示 1/3 而相机按 1/2.5 曝光属于误导。

全档位表验算：46 个档位（含长曝光段），最大显示偏差 4.17%，相邻档步进全部符合 1/3 档（×1.15~×1.40）。

**✅ 长曝光档位已补齐（2026-09-01 用户拍板）**：`ShutterCatalog.VALUES` 从 27 档扩到 **46 档**，
新增 `raw 5000`（0.5s）→ `raw 300000`（30s）共 19 档，按 1/3 档递进（与 Nikon 机身 M 档步进一致）：

```
1/2 → 1/1.6 → 1/1.2 → 1s → 1.3s → 1.6s → 2s → 2.5s → 3.2s → 4s → 5s →
6.4s → 8s → 10s → 13s → 16s → 20s → 25s → 30s
```

- B 门（`ShootingState.BULB`）不在档位表内，独立控制，互不影响
- `setShutterSpeed` 的上下限限位取档位表首尾（10 → 300000），越界自动 clamp，无需改动
- 滚轮（`resolvePickerIndex` / `stepIndex`）全部动态基于 VALUES，自动适配 46 档

**回退点**：令 `apertureOptions()` 恒返回 `ApertureCatalog.FALLBACK` 即回到固定 11 档，快门修复仍生效。

**改动文件**

- `camera/gallery/TransferFragment.kt`

> 本分支取代了第一版 `feat-album-sort-order`。第一版依据 object handle 排序、只支持两档切换，
> 且无法作用于本地相册；这一版改为**按真实拍摄时间 / 文件类型**排序，两个维度各支持升序与降序。

**第一步（T6 初版）解决的问题**：相机相册此前没有任何排序，直接沿用 `fetchPhotoList()` 返回的
对象句柄顺序（旧→新），新拍的照片落在列表最底部。

### 排序维度与默认方式

| 维度 | 取值来源 | 说明 |
| --- | --- | --- |
| **拍摄时间**（默认） | 相机侧：PTP ObjectInfo 的 `DateCreated`，缺失回退 `DateModified`<br>本地侧：MediaStore 的 `DATE_TAKEN`（系统索引时已从 EXIF 提取），缺失回退 `DATE_MODIFIED` | `CameraFile.captureTimeMillis`，降到毫秒 |
| **文件类型** | 以**扩展名**为准分组：照片 → RAW → 动图 → 视频 → 其他，组内再按扩展名、文件名排列 | 动图（`.GIF` / `.APNG` / `.WEBP`）在 PTP 的 ObjectFormatCode 里没有独立分类，按枚举分不出来，只能按扩展名分 |

每个维度均支持 **升序 ↑ / 降序 ↓**，共 4 个选项。
**默认「拍摄时间 ↓ 降序」**，即新拍的照片排在最前面，与常见相册一致。

### 时间缺失的兜底逻辑

`captureTimeMillis == null` 的文件（相机没写 DateCreated/DateModified、本地 DATE_TAKEN 与
DATE_MODIFIED 都取不到）**恒定排在「有时间数据」的文件之后，升序降序都不翻转**，组内再按文件名升序。
这样它们不会在升序时霸占首屏把真实照片挤到后面；组内按文件名排是为了多次刷新顺序稳定。
注意本地侧两个列量纲不同：`DATE_TAKEN` 是毫秒、`DATE_MODIFIED` 是秒，回退时已 ×1000。

### 实现要点（对应需求 1~6）

| 需求 | 做法 |
| --- | --- |
| 1 排序入口 | 顶部工具栏的排序 chip 改为 `PopupMenu`（与 `LiveViewFragment` 的「更多」菜单同一实现），当前规则以勾选态标记 |
| 2 持久化 | `AppSettings.albumSortDimension` / `albumSortDirection` 存枚举名，读取失败回退默认；排序在 `displayedPhotos` 之后统一处理，切相册、切目录都走同一条链路 |
| 3 时间兜底 | 见上节 |
| 4 不破坏既有功能 / 全量排序 | 所有批量操作都基于 handle 集合，与列表顺序无关；**分页期间跳过排序**（`_isLoading` 为 true 时原样透传），加载完成后对**完整数据集**排一次，避免每页重排导致跳动 |
| 5 性能 | 排序是纯函数，跑在 `Dispatchers.Default`；配合 `mapLatest`，新数据到达时取消上一次未完成的排序；文件类型排序**预计算排序键**，避免 O(n log n) 次字符串切分与小写转换 |
| 6 立即刷新 + 保持滚动位置 | 排序变更即触发 Flow 重算；切换前用 `captureScrollAnchor()` 记下首屏第一项的 handle，重排后 `restoreScrollAnchor()` 把它滚回视野顶部 |

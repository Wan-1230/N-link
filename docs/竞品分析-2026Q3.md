## 0. 取证方法与证据等级

本文的每条结论都标注证据等级。竞品多为闭源、私域分发，**不看证据就写对比 = 编故事**，所以先把口径立清楚。

| 标记 | 含义 | 来源 |
|------|------|------|
| 【实】 | 代码/产物直接确证 | 本仓库源码 `文件:行号`；或竞品 APK 静态分析产物 |
| 【官】 | 厂商官方页面/说明书原文 | nikon.com.cn / nikon.co.uk / 在线说明书 / App Store 商店页 |
| 【网】 | 公开网络二手信息，**可信度待核** | 第三方综述、开发者自宣视频 |
| 【推】 | 由上述证据推导的判断，非事实 | 本文作者 |

**取证手段**（竞品闭源，只能黑盒 + 结构分析）：

- `aapt2` Manifest/badging 解析 → 权限、SDK 版本、包名、组件：`_apk_re/badging/*.txt`
- DEX 类清单与字符串扫描 → 协议常量、私有命令码、日志文案（**日志文案是竞品把自己的设计写给自己看的东西，信息密度最高**）：`_apk_re/dex/`、`_apk_re/scan/*.txt`
- 原生库导出符号（含未剥离的 C++ mangled name）→ 还原 SDK 类结构：`_apk_re/so/`
- 反汇编取证主机注册流程：`_apk_re/zdrop_hostreg_disasm.txt`
- 法律边界：**全部为公开分发物的结构与字符串分析，不复制任何竞品代码**；`libcamerawirelesscontrol.so`（像素蛋糕内第三方商业 SDK）仅用于理解行业做法。

**不可得清单（诚实记录）**：ZDROP、ZRelay、影犀三款在公开网络**没有可查的商店页/官网/定价页**（Google Play、国内容器、知乎、B 站、小红书均无有效条目，ZRelay 仅有开发者自宣视频）。它们的版本号、能力面、私有命令**只能靠 APK 取证补齐**。这本身是一个结论：**这条赛道没有公开可比的商业情报，谁先做出「可被搜索到的、有真机数据的」产品，谁就拿到信任红利。**

**判断【推】**：这不是一个「我们 vs 官方」的赛道，而是**官方能力缺口的填空竞赛**。尼康官方 App 的每一个硬限制（2MP、无 USB、后台不传、云端服务关停）都是第三方存在的理由；反过来，官方每一次「免费化」（影速传 1.6.0）都会直接压缩第三方的卖点空间（见 §5）。

## 2. 逐家档案

### 2.1 SnapBridge（尼康官方）— 所有人的反面教材

| 项 | 内容 | 证据 |
|---|---|---|
| 包名/版本 | `com.nikon.snapbridge.cmru` 2.13.3；Android 国内包停在 2.12.0 | 【实】`_apk_re/badging/SnapBridge_v2133.txt`【官】商店页 |
| 通道 | BLE + 蓝牙经典(SPP) + WiFi AP/STA；**无 USB host**（不声明 `android.hardware.usb.host`） | 【实】Manifest |
| 技术栈 | Java/Kotlin + 3 个尼康自研原生库：`libNis.so`（NIS 云）、`libJuno.so`（EXIF）、`libLsSec-jni.so`（BLE 凭据加密） | 【实】`_apk_re/so/` |
| 配准 | Bonjour `_ptp._tcp.` + GUID 配对；用 PTP **厂商操作读写相机 WMA 设置**（SSID/WPA 密码/信道/认证/WPS） | 【实】类名 `GetWmaSettingAction`/`SetWmaSettingAction`/`BonjourPairingTask` |
| 能力边界 | 自动传图仅 **2MP web-ready**；大尺寸 JPEG/视频需手动；**后台运行时不自动上传**、位置仅前台下载 | 【官】[Nikon UK 产品页](https://www.nikon.co.uk/en_GB/product/apps-software/snapbridge)、[Z8 说明书](https://onlinemanual.nikonimglib.com/z8/zh-cn-prc/problems_and_solutions_371.html) |
| 更新动向 | 一年 3–5 版，内容基本是「新增机型支持 + 修小缺陷」；2.13.3 发布于 2026-01-06 | 【官】App Store 版本史 |
| 口碑 | 中国区 iOS 4.7/18428 评（商店口径），**但第三方聚合口径 1.9/5、1 星占 64%**；中文社区高频词「乐色/玄学连接/配对失败/只给小图/NEF 传不了/后台一杀就断」 | 【网】+【实】我们自己的群反馈 |
| **生态地震** | **Nikon IMAGE SPACE / 影像馆 2026-10-15 终止服务**，接棒的 Nikon Imaging Cloud **仅 Z6III/Z5II/Zf/Z50II**；2024-04 尼康中国曾一次性下架全部安卓官方 App（备案问题） | 【官】[尼康中国 Apps 页](https://www.nikon.com.cn/sc_CN/service/app.page)、[IT之家](https://www.ithome.com/0/994/605.htm) |

**对我们的三条直接冲击**【推】：
1. 官方永远不做 USB 有线、不做原图批量、不做低延迟监看 —— 这是我们的**结构性护城河**，不是功能优势。
2. 影像馆关停会把一批「云端备份」用户推到本地/网盘工作流，是**传原图 + 不上传云**叙事的窗口期。
3. 官方 App 有合规停摆先例 → 我们「纯本地、无云端依赖、开源可审计」可以作为**卖点写进对外文案**。

### 2.2 影速传 NX MobileAir（尼康官方专业传图）— 2026 年最被低估的威胁

- 【官】官方页原文：**「自 1.6.0 版本起 Android 专业版将解除对相册和保存文件的功能限制，现可免费下载使用。」**
- 【官】能力：**USB 有线联机**取图 + 经 4G/5G 向 FTP 服务器推送；Z9/Z8/Z6III 支持 Frame.io 上传；iOS 无线传输与遥控连拍限 Z9/Z6III 且需 iOS 17。
- 【推】**这是官方第一次把「有线联机 + 原图」免费化**，正面打在我们「USB 读卡 + 传原图」的核心卖点上。它的弱点同样明显：面向商业工作流（棚拍/体育/图片直播），**没有实时监看工具、没有遥控拍摄参数面、没有 B 门/间隔、没有 LUT/波形、不做 BLE 保活**，且强依赖云端上传链路。
- **对策**【推】：不要在「官方已经免费做的部分」上纠缠，把叙事挪到官方做不到的三件事：**机身参数全量遥控 + 低延迟监看工具 + 一次配对长期自动恢复的稳定性**。

### 2.3 ZDROP（`com.zdrop.z6ii` 1.0.257）— 无蓝牙兜底的极端工程派

| 项 | 内容 | 证据 |
|---|---|---|
| 体量/栈 | **3.1MB**，纯 Kotlin + Compose，单 dex，**零第三方网络库**（无 OkHttp/Retrofit） | 【实】`_apk_re/badging/ZDROP_1.0.257.txt`、`dex/classes_ZDROP-1.0.257.txt` |
| 通道 | AP + 手机热点 STA + 同路由 STA + USB host；**完全不声明蓝牙权限** | 【实】Manifest（无 `BLUETOOTH_*`） |
| 关键手法① | **不硬编码 IP：从已连网络的 DHCP/路由信息学出相机地址**（网关即相机），并做「稳定化」与「排除手机自身地址」 | 【实】字符串 `AP gateway detected host=` / `AP gateway stabilized host=` / `AP gateway ignored because it matches handset address=` |
| 关键手法② | NSD 发现 + resolve 队列 + `/24` 扫描 + **仅 TCP 可达性探测**（不抢会话）；热点模式额外等相机拿租约（`AP network readiness wait=1200ms`） | 【实】`PtpIpProbe` 类与字符串 |
| 关键手法③ | **双 data 通道**、断点续传、按阶段(phase)打点重试 | 【实】`… retry requested phase=`、`channel retry scheduled failedAttempt=` |
| 相机热点识别 | SSID 规则 `(?i)^NIKON_([0-9A-F]{8})` | 【实】DEX 字符串 |
| 主机注册 | `0x952B`(PrepareHost) / `0x935A`(ConfirmHost) 流程的**原始出处**（我们的实现来自其反汇编） | 【实】`zdrop_hostreg_disasm.txt` |
| 商业/分发 | 【网】公开网络查无商店页与定价 —— 私域分发 | — |

**启示**：AP 通道跨机型不稳的第一根因是「会不会学网关」，而不是 ROM 差异。我们已照此落地 `ApGatewayResolver.kt`（v2.2 G1，已验证）。**它没有 BLE，所以每次连接都必须把网络侧做对** —— 这解释了它把工程量全压在发现/探测上。

### 2.4 ZRelay 相机快传（`com.geekmanlab.zrelay` 3.0.46）— BLE 主导 + 兼容治理最重投入者

| 项 | 内容 | 证据 |
|---|---|---|
| 体量/栈 | 3.2MB，Kotlin + 极小 native（`libzrelay_core.so` 仅 `JNI_OnLoad`，PTP 栈在 native 侧 C++） | 【实】badging、`dex/classes_ZRELAY.txt` |
| 通道 | **BLE 配对 + WiFi**；**无 USB host**；**不声明 `CHANGE_WIFI_MULTICAST_STATE`**（→ 不做 mDNS 发现） | 【实】Manifest |
| 关键手法① | **`TetheringManager` 主动开/感知本机热点**（`TetheringEventCallback`/`TetheringInterface`），再用 BLE 把热点 SSID/密码写给相机 → 用户不用手工开热点 | 【实】`Landroid/net/TetheringManager$TetheringEventCallback;` |
| 关键手法② | 重连状态机：BLE 扫描窗口 + 候选打分 + **拒绝原因可见**（`reconnect_scan_window_elapsed`、`reconnect_candidate_matched/rejected`、`ReconnectingAfterBond`） | 【实】`scan/ZRELAY.txt` |
| 关键手法③ | **兼容规则放服务端下发**（`/v1/camera-rules`） | 【实】API 路径字符串 |
| 合规 | **targetSdk 36（Android 16）**，比我们高一档 | 【实】badging |
| 商业/定价 | 【网】免费 + 约 ¥20 一次性 Pro（非订阅），RAW/JPEG 下载与断点续传，v3.0 加光圈/ISO/WB/快门/实时取景；**经 B 站私信与官网分发，无商店上架** → 综述明确指出「带来隐私与持续维护疑虑」 | 【网】[smzdm 综述](https://post.smzdm.com/p/a958wn95/)（**AI 聚合稿风险，价格与版本需以 APK 复核**） |

**启示**：①「机型×ROM×通道」矩阵必须当产品资产建 —— 它是同类里唯一在这一点上重投入的，且用服务端下发做到不发版修兼容；我们已把规则数据化为 `assets/compat/rom_rules.json`（6 家族/19 条），**但没有热更新通道**（G21 未做）。②`TetheringManager` 是我们唯一的结构性空白（G4 全仓 0 命中），能把 STA 从「用户手工开热点 + 相机手工连」压成一步。③targetSdk 36 是必须跟进的合规项。

### 2.5 影犀 / CameraSync Pro（`com.camerasyncpro.app` 1.2.1）— Flutter 多品牌路线

- 【实】Flutter（Dart 逻辑在 `libapp.so`）+ 原生 USB 插件；73MB；minSdk 26 → **targetSdk 36**；USB + PTP/IP，多品牌（尼康/佳能/富士/索尼/松下/GoPro/佳能 BJNP）。
- 【实】**九种 mDNS 服务类型枚举**：`_ptp._tcp`、`_nikon._tcp`、`_nikon-ptp`、`_nikon-pc`、`_camera-canon._tcp`、`_fujifilm._tcp`、`_sony._tcp`、`_panasonic._tcp`、`_gopro-web._tcp`… （**我们只监听 2 种**：`WifiScanner.kt:88-89`）。
- 【实】STA 侧三个子状态：`nikonStaInitAckOnly` / `nikonStaPairingConfirmed` / `NikonStaConnectionIntent` —— 把「STA 连不上」拆成可诊断的子阶段，与我们 `ConnFunnel` 的思路一致，**但它的 STA 子状态比我们的 Stage 更贴近尼康语义**。
- 【实】内置 **40 个 33³ `.cube` LUT**（Color Grading Central / Denver Riddle 版权，**不可照抄**）+ 10 个水印模板 + exiftool；**无自定义 GLSL** → 推断 LUT 用于后期导出而非实时监看【推】。
- 【网】公开网络仅 2026-08-25 一篇综述提了一行「刚起步，观望，支持尼康佳能」。

**启示**：多品牌是它的广度优势，也是它的深度天花板 —— 每个品牌只能做到 PTP 公共子集。我们做单品牌深耕，**必须把尼康私有语义吃干**（我们已做到：拍摄后逐张 `ObjectAddedInSDRAM` 入册、`LiveViewProhibitCondition` 禁读原因、0x9207→0x100E→0x100F 三级快门降级）。mDNS 类型枚举数与 STA 子状态数是**低成本可抄的两件事**。

### 2.6 像素蛋糕 PixCake（`com.xiangtian.pixcake` 1.9.2）— 花钱买 SDK + 订阅制

- 【实】内置第三方商业 SDK `libcamerawirelesscontrol.so`（**111 个 `NikonCameraControl::` 符号**）→ 走「授权/购买 SDK」路线，自研成本最低，能力面受限于 SDK。
- 【官】小米商店 Android v1.9.2（2026-09-14）；**订阅 ¥19.9/月 或 ¥198/年**；主业 AI 修图，「联机拍摄」是前端入口；官方 wiki 列索尼/佳能/尼康/富士/理光。
- 【推】**它证明了两件事**：这条链路有人愿意付订阅费；「AI 修图 + 联机」是可以互相导流的组合（我们 Phase 4 的 AI 修图 PRD 与此同构，但我们不能买 SDK、只能自研协议，因此工程门槛远高于它）。

### 2.7 帧澈 ZENCHE（`Tauber01/ZENCHE`，MIT，125★，v1.5.15）— **威胁最大的同路人**

> 用户点名的「帧澈」是**开源项目**，不是 APK。这是本次分析里唯一能读到全部源码的对手。

- 【实】五端原生：macOS(SwiftUI + libgphoto2)、**Android(Views + USB Host，语言是 Java 1.25MB)**、Windows(WPF/.NET8 + libusb)、HarmonyOS(ArkUI)、iOS。唯一贡献者 62 commits，仓库创建 2026-07-28，**最后 push 2026-08-22（距今已 29 天无提交）**；27 个 release，一个月内平均 1.6 天一版。
- 【实】协议栈：TCP 15740 双通道（command + event），**Live View 用尼康私有 op `0x9201` 开 / `0x9202` 关 / `0x9203` 取帧（data-in 返回 JPEG）**，录像 `0x920a/0x920b`；取帧循环**约 10fps**，单帧失败 300ms 退避；外录为流式 Motion-JPEG AVI。
- 【实】能力面：50 款机型档案（20 Nikon 含 Z9/Z8/Zf/Z6III/Z50II/Z5II/ZR，16 Sony + 14 Canon **均标注「实验性，待实机验证」**）；`.cube` LUT（`CubeLut.java`）、**RGB 三色叠加波形 + 矢量示波器**、直方图、峰值对焦、假色、斑马纹、**107 款尼康云创 NP3 预设 SDR 近似监看**；间隔/包围/焦点包围/B 门；机内存储浏览 + 批量下载 + 删除；FTP/HTTP/WebDAV 收件箱；XMP GPS 旁车；RAW+JPEG 配对；**AI 修图/生图**。
- 【实】**它的「开源」只有客户端**：AI 是 `zenche.top` 闭源云服务 + 设备绑定激活码 + 爱发电付费兑换码。桌面端**接入专有 Nikon Remote SDK 2.0.0 + Image SDK 1.46.0 二进制**（不入库，README 自述「官方运行库属于尼康专有组件」）。
- 【实/推】死穴：①**BLE 不是相机配对** —— 只有 `BluetoothRemoteController`（自家蓝牙遥控快门），全仓搜 `0x952B`/`_ptp._tcp`/`SnapBridge`/`blowfish` **0 命中**，即它**没有尼康 BLE 配对协议实现**；②无 RAW 解码，NEF 预览靠系统；③Android 包是 **debug 证书签名**、iOS 未签名、Windows 无 Authenticode；④开放 issue #44「Win11 安装后打不开」，官网更新通道仍停在 1.5.14；⑤无线收件箱默认口令 `nikonlink:nikonlink` 且无 TLS；⑥Sony 实时取景/录像标注「不支持」；⑦自 8/22 起停更。
- ⚠【实】**命名冲突**：`github.com/Tauber01/NikonLink` **永久重定向到 ZENCHE**，其 v0.4.0–v0.8.1 的 release 标题就是「Nikon Link」（2026-07-28/29），README 明说目录/scheme/**包名 `com.tauber.nikonlink` 永久保留**。我们首提交 2026-08-02（`Initial commit: NikonLink Android app`），`applicationId = com.nikonlink.app` —— **对方早 5 天，且握有 GitHub 搜索与外链权重**（详见 PRD FR-20 品牌决策）。

**威胁判断【推】**：帧澈构成的是**叙事威胁**而非工程威胁 —— 它的「五端 + LUT + 波形 + AI + 批量 RAW + 文件库/备份/哈希」在 README 层面完胜我们的功能表，但它没有尼康 BLE 配对、Android 端是 Java/debug 签名、且已停更 29 天。我们的应对不是追功能清单，而是**把「连接成功率 + 真机验证 + 每周发版」这三件它能说但我们能证明的事做穿**，同时把它已验证的需求方向（LUT/波形/包围/焦点包围/RAW 配对）作为我们的 P1 输入。

### 2.8 ZTransfer（`RealCaCl2/ZTransfer`，v1.0.2，2026-08-21，★6，**无 License**）— 同平台同细分的后起者

  > `// Nikon "Connect to computer" mode — opcodes provided by libztransfer_core.so`
  > `// The previous hardcoded values (0x9010, 0x9435, 0x935A, 0x952B, 0x9431, 0x9400) were ALL wrong and caused the camera to reject every private operation.`
- 【推】**这是本次分析里最需要立刻处理的技术事项，但结论要读准**：① 对方明确把这套码限定在 **Nikon「Connect to computer」模式**，而我们的 `0x952B/0x935A` 服务的是 **SnapBridge 系的 WMA 主机注册**（`zdrop_hostreg_disasm.txt` 取证，且真机跑通）→ **两条通路并存的可能性远大于「谁错了」**，不能因为这句话就把已验证的代码判死。② 真正需要立刻核对的是 **GetEventEx**：我们代码里只有 `OP_NIKON_CHECK_EVENT = 0x90C7`（`PtpProtocol.kt:96`），**全仓不存在 `0x9714`**；而 `PtpSessionManager.kt:321-322` 的注释把这个调用写成「Nikon GetEventEx (0x90C7)」——**命名与注释自相矛盾**（0x90C7 按标准命名是 CheckEvent，只问「有没有事件」，不取事件数据）。若 `0x9714` 才是带事务号回取事件体的 GetEventEx，**我们可能一直在用「只查不取」的调用**，这与 GAP-05「数据期丢事件」是同一根链上的两个症状。③ `0x9A6C` 高速局部对象下载若成立，是全场唯一一次下载速率跃升的机会。以上全部列入 PRD FR-14 探测专项。

## 4. 四条技术路线的取舍（这才是差异的根源）

| 路线 | 代表 | 得到什么 | 付出什么 | 我们的位置 |
|---|---|---|---|---|
| **A. BLE 主导**（配对/凭据/保活全走蓝牙，WiFi 只搬数据） | ZRelay | AP 稳定性最好；可主动开热点；免手工输入密码 | **强依赖机身支持 BLE 配对**；新固件用 LsSec 加密 `0x2004` 凭据后不可解 | 我们已是 BLE 主导派，但**没有 TetheringManager**（G4），BLE 侧只做了配对/心跳，`0x2006` 写时间、`0x2007` 写位置**一个都没实现** |
| **B. 纯 WiFi/USB**（无蓝牙兜底） | ZDROP | 无配对依赖，兼容不支持 BLE 的老机身；工程全压在网络发现 | 一旦相机不广播/路由隔离就没有第二把钥匙 | 我们的**降级路径**：AP 免蓝牙直连已在 v2.2 G2 落地（`AP_BLELESS`） |
| **C. 买第三方 SDK** | 像素蛋糕 | 最快上线、多品牌、免逆向维护 | 能力面受限于 SDK；**尼康并无面向第三方的移动端 SDK**，桌面授权库拿不到 | 结构上**不可复制**（尼康不发移动 SDK），这是我们的天然壁垒 |
| **D. 多端原生/跨平台** | 帧澈(五端)、影犀(Flutter) | 覆盖广、平台多 | 每端一套真机验证；**iOS 根本拿不到尼康 USB/PTP 控制**（帧澈自述需 Mac 桥接）；Flutter 的原生 USB/GATT 桥接层是稳定性黑洞 | 我们**主动选窄**：Android 单端 Kotlin 单栈。这是正确决策，别动摇 |

**决定性事实**（来自既有调研，反复验证）：尼康不向第三方提供移动端 SDK；Z 系列无 HTTP/Web Server 兜底（官方 WMU 明示「无法与兼容 SnapBridge 的相机配合使用」）；**机身同一时刻只允许 1 个 PTP/IP 客户端**。
→ 【推】**推论 1**：这条赛道的技术门槛是「逆向 + 真机矩阵」，不是架构；**推论 2**：机身单客户端约束意味着**我们和 SnapBridge 是互斥的**，谁的引导做得好谁赢；**推论 3**：任何声称「更简单方案（官方 SDK/HTTP）」的想法都是死路，不要回头再查。

## 5. N-Link 的定位与差异

### 5.1 一句话定位

> **面向尼康 Z 系列的开源 Android 连接与遥控工作台：把官方 App 做不到的（有线、原图批量、全量参数遥控、低延迟监看）做到可用、可诊断、可回退。**

### 5.2 三个结构性优势（对手短期难以复制）

1. **尼康 BLE 配对协议的 Android 原生实现 —— 全行业（含全部开源项目）唯一。**
   【实】`BleManager.kt:68` 四阶段配对 + `:939-949` `NikonBlowfish`（Blowfish/ECB/NoPadding）+ `NikonBlowfishTest.kt` 向量测试。帧澈搜 `blowfish/0x952B/_ptp._tcp` **0 命中**；ZRelay 闭源无法比对；SnapBridge 用 LsSec 加密且不外发。
2. **BLE + WiFi(AP/STA) + USB 三通道全量打通，且带统一诊断。**
   【实】12 Stage / 40 稳定原因码 `ConnFunnel` + 9 项 `PreflightGate` 预检 + `rom_rules.json` 机型引导。**ZDROP 无蓝牙、ZRelay 无 USB、帧澈无 BLE 配对** —— 三家各缺一角，我们全有。
3. **开源 + 纯本地（不上传照片）+ 双网盘分发。**
   在官方 App 有停摆先例、ZRelay 无商店上架被质疑隐私、帧澈「开源只在客户端（AI 是闭源云+兑换码）」的对照下，这是**唯一可被审计的可信性**。

### 5.3 三个结构性劣势（不要粉饰）

1. **监看是「够用」而不是「好用」**：15fps 硬编码 + 全 CPU 解码 + ImageView 上屏 + 仅亮度直方图，**没有一个监看工具（LUT/波形/峰值/斑马）**。帧澈有可调帧率 + 波形 + LUT，影控台有示波器 + LUT + 峰值，**监看工具是「专业感」的来源，我们这块是空的**。
2. **拍摄能力缺包围与焦点包围，RAW 工作流缺配对策略**：包围/焦点包围全仓 0 命中；RAW+JPEG 配对下载未实现；RAW 分享副本代码里写着「本版未实现」。**风光/产品摄影的用户在这三项上会被帧澈直接拿走。**
3. **工程质量基建比竞品薄**：无 CI、无 instrumented 测试、无崩溃上报、无英文、兼容矩阵 9/13 条从未真机验证、`proguard-rules.pro:4` keep 了一个**不存在的包**（`app.core.ptp` 实为 `app.device.ptp`）、targetSdk 落后一档、**仓库无 LICENSE 文件**。我们对外说「开源可信」，但可信性的基础设施本身有洞。

### 5.4 差异化叙事（对外怎么说，一页）

| 对手 | 我们比它强的那一句 |
|---|---|
| SnapBridge | 「原图 + NEF + 有线 + 遥控 + 监看，官方一样都没有；影像馆 10/15 还要关停。」 |
| 影速传 | 「它是商业传图前端，我们是拍摄工作台：B 门、间隔、包围、实时监看、参数全量读写。」 |
| ZDROP | 「它有网络工程没有蓝牙兜底；我们三通道 + 同一套诊断，且开源可审。」 |
| ZRelay | 「我们 USB 有线 + 包围之外全都有，且不发版也能改的兼容矩阵 + 商店之外的透明分发。」 |
| 帧澈 | 「同一件事 Android 单端做穿 > 五端做浅：BLE 尼康配对它有不了，真机验证它有『待实机验证』，我们每周发版。」 |
| 像素蛋糕 | 「不订阅、不上传、不依赖云；相机数据一个字节不出手机。」 |

## 8. 机会窗口（3–6 个月）

1. **影像馆关停（2026-10-15）** → 官方云备份用户被迫迁移，「本地 + 网盘 + 不上传」叙事窗口，**时间敏感**。
2. **帧澈停更 29 天 + iOS 无法直连尼康** → 开源阵营的「五端叙事」正在失速，我们若补齐监看工具 + 包围/焦点包围 + RAW 配对，就能在**同一批需求**上形成「单端做穿」的对照。
3. **ZRelay 无 USB、无商店上架** → 「有线 + 可审计 + 开源」的组合它短期补不上；它 3.0 刚进遥控，正是拉开身位的时候。
4. **影速传免费化** → 正面冲突已开始，**必须**在对内文案与 App 内引导里把差异说清楚，否则用户会问「官方都免费了为什么还要装你」。
5. **机身单 PTP/IP 客户端约束** → 官方 App 用户量越大，「和 SnapBridge 冲突」的抱怨越多。**做一个「检测到占用 → 一键引导腾挪」的功能，是竞品都没有的、只有我们能做的、且直接消解最高频差评的点。**（→ PRD FR-14）
6. **`0x9A6C` 高速局部对象下载**（若真机成立）→ 全场唯一的速率跃升机会，且开源界无人做到。

## 1. 「开始连 WiFi 时返回给相机的报文」到底有什么（任务 1）

### 1.1 日志能力边界（先说死，避免伪证）

本机导出环（`AppEventLogger`，3×512KB）只记录**事件字段**，不记录 socket 收发字节；
ZDROP 诊断 likewise（只记 phase 与个别响应 hex，如 `prepare=0400000002050808`，那是**相机→ZDROP** 方向）。
因此「完整报文」在四份日志里**不存在**，任何声称从这些日志里抄出完整 TX 报文的说法都是编造。
下面给出的是「日志时间戳 × 代码发送点」双向重建的字段级清单。

### 1.2 字段级重建：配网（注册）链路我们→相机的全部写入

协议：PTP/IP（ISO 15740），TCP 15740，command/event 双通道。发送点代码：
`StaHostRegistrar.kt`（未连接态自主注册，FR-30）与 `PtpSessionManager.registerHost()`（已连接态）。

| 时间戳（n-link …8220927） | 通道 | 我们→相机的报文（字段级） | 相机→我们的响应（日志记录到的状态码） |
|---|---|---|---|
| 01:19:05.323 `hostreg phase=start` | command | `InitCommandPacket{clientGuid=持久化16B GUID, clientName=Build.MODEL("V2509A")}` | 01:19:05.406 `InitFailPacket{reason=1}`（connection_in_use） |
| （同轮之前 01:18:47→01:19:05 扫描段） | command | 扫描确认探针对每个候选发 `InitCommandPacket{clientName="N-LinkProbe"}`（`PtpIpProbe.probeDetailed`，旧行为） | 候选回 InitAck（=占槽开始） |
| 01:19:40.688 第二轮 start | command | 同上 InitCommand | 10s 无响应 → `SocketTimeoutException`（01:19:50.701） |
| 01:33:13.404 / 01:34:02.657 第三/四轮 | command | 同上 | `.731` / `.778` 再次 `InitFail reason=1` |
| （ZDROP 对照 2026-10-01 23:27:12.042→21.056） | command+event | `InitCommand` → `InitEventRequest{sessionId}` → `GetDeviceInfo(0x1001)` → `OpenSession(0x1002, param=1)` → `PrepareHost(0x952B, 无参)` → 等 8.5s → `ConfirmHost(0x935A, param=0x2001)` | 全 OK；`prepare` 响应体 `0400000002050808` |

我们的注册序列与 ZDROP 成功序列**逐字段同构**（操作码、顺序、OpenSession 参数 1、
ConfirmHost 参数 0x2001、8.5s settle 均一致；见 PRD §13.6 与 `PtpConstants`）。
唯一内容差异是 `clientName`（我们=机型串 / ZDROP=自定义名）与 GUID 值——二者都只影响
相机确认界面的显示名，不影响受理（`已验证`：ZDROP 换过两个名字都成功）。

### 1.3 AP 链路我们→相机的写入（对照用）

建链期：`InitCommand` / `InitEventRequest` / event 通道 `Ping`（随后对相机 ProbeRequest 回 `Pong`，
`PtpSessionManager.kt:1130`，不回则相机主动断）/ `GetDeviceInfo` / `OpenSession(1)` / `CheckEvent(0x90C7)` 排空。
** teardown 不发 CloseSession(0x1003)**：`closeSession()` 只关 socket（`PtpSessionManager.kt:923-932`）——
即我们在 WiFi 路径上从未向相机发过会话关闭命令，「关热点」不可能由一条 CloseSession 触发（`已验证`）。

## 2. 时序梳理：AP 成功链 vs 配网失败链（任务 2）

### 2.1 链 A：AP 连接成功（n-link，02:09:38–02:09:57）

```
02:09:38.682 conn_attempt user_tap（AP-fallback），ap_ctx on_camera_ap=true
02:09:41.016 ap_gateway 192.168.1.1 stable
02:09:45.533 sta_fallback ifaces=ccmni4+rndis0 in_subnet=false   ← wlan0 此刻不在
02:09:48.745 preconnect TIMEOUT（从蜂窝探，必然空）
02:09:57.472 socket_try n=1 ECONNABORTED 8.7s → n=2 ok 51ms      ← wlan0 回归，子网路由生效
02:09:57.832 init ok → .841 event ok → .872 established → pair_ok
02:10:07.817 下一次 conn_attempt 时 ap_ctx on_camera_ap=false；ap_probe ×4 TIMEOUT ← 热点已没了
```

### 2.2 链 A2：AP 成功后 +7.3s 死亡（n-link，01:37:23–01:37:32）

```
01:37:23.192 wifi_sta network_restored → 自动恢复 gen=3
01:37:23.959 init ok → .972 event ok → 01:37:24.302 device_caps ops=130 → .327 established
01:37:31.661 link_error reason=event_read_error                  ← 相机侧关闭，间隔 +7.3s
01:37:32.123 gen=4 TCP 建链成功，但 init 永远无 ack               ← 相机 PTP 服务已不在（热点收尾中）
```
**两段 A/A2 在 established 与死亡之间，日志里没有任何 hostreg/配网事件，也没有新的发送点记录** ——
即「AP 成功后掉线」与「开始配网」在本日志中**没有时序交叠**（`已验证`）。

### 2.3 链 B：配网（注册）失败（n-link，01:18–01:34，4 轮）

```
每轮：discover_start →（扫描：mDNS/网段/ARP/NSD + InitCommand 确认探针）→ discover_hit
      → hostreg start → 83~327ms 内 InitFail reason=1（或一次 10s TCP 超时）
相机侧（用户目视，不在日志）：提示「连接失败」→ 关闭热点/退出向导
```

### 2.4 链 C：ZDROP 对照（两份 ZDROP 日志）

- 注册成功链（10-01 23:27）：发现提交 → **8s 后**才开注册链路 → 全序列 OK → 相机正常保存配置。
- AP 链（10-02 01:40）：连续 5 次 `INIT_EVENT Connection reset`（相机→ZDROP 方向 reset），
  **相机热点全程未关**（每次重试都能拿到 init-command-ack）；热点最终在会话存活 34s 后才消失。
- 对照含义：① 同样的报文内容在 ZDROP 手里成功 → 内容无罪；②  even 连续握手失败也不会让相机关热点 →
  「关热点」不是握手失败的通用后果，而与我们链 B 的**高频半开 init（扫描探针+注册 init 背靠背）**共现。

### 2.5 差异汇总

| 维度 | AP 成功链 | 配网失败链 | ZDROP 注册成功链 |
|---|---|---|---|
| 发起前对相机的 init 次数 | 0（直连） | 扫描段 N 次（254 段扫+ mDNS 确认）+ 注册 1 次，**背靠背** | 发现段若干，但注册前留了 8s 空窗 |
| 注册 init 与上一次 init 的间隔 | — | 83~327ms | ≈8000ms |
| 相机响应码 | init ok | `InitFail reason=1` ×4 | init ack |
| 相机后续行为 | 会话建立（之后另因死亡） | 用户目视「连接失败」+ 关热点 | 保存配置、继续服务 |

## 3. 根因判断（任务 3）

### 3.1 「响应内容导致相机判失败」——不成立（三条反证）

1. **内容同构反证**（`已验证`）：§1.2 表 vs ZDROP 成功序列逐字段一致；同机身同固件，内容若有害 ZDROP 不会成功。
2. **拒绝码语义反证**（`已验证`）：日志里相机给我们的唯一拒绝是 `reason=1 connection_in_use` ——
   语义是「槽位被占」，属**状态**而非**内容**；若报文字段非法，尼康向导态的回包应是
   `0x201F/0x2005` 一类事务/参数错误码，四轮的 `device_caps`/`hostreg` 事件里**一次都没出现**。
3. **可观测性反证**（`已验证`）：现有日志不含 TX 字节，「内容有害」在当前证据下**不可证伪**；
   按本项目证据规则，不可证伪的假设不得作为改动依据（红线：已跑通的 AP 链不许拿去做实验田）。

### 3.2 真正的切入点

**切入点 1（已验证，已落地待真机验）：配网发现阶段的 InitCommand 探针占槽。**
扫描对候选发 init → 半开会话占住唯一槽（机身收回需数十秒，FR-21 实测）→ 注册 init 83~327ms 后到 →
`reason=1` → 用户重试 → 又一轮探针+init → 向导态相机被连续半开 init 轰炸 →
相机放弃向导（外在表现=「连接失败」+ 关热点，`推断待验证` 的最后一步）。
对应修复即 FR-31③：注册发现 `ptpConfirm=false` 全链路只 TCP 筛探（代码已落地，真机待验）。

**切入点 2（推断待验证）：注册重试节制。** 即便发现不再占槽，外部占槽（别的 App、上一轮残留）
仍可能给出 reason=1。现状是用户连点=立即重轰。建议：收到 reason=1 后按机身收回窗（≥35s，FR-21 实测）
冷却再试，单向导会话内注册 init ≤2 次。

**切入点 3（推断待验证）：AP 会话 +7~10s 死亡是另一条线，与配网无关。**
候选死因（按证据强度）：① 手机侧接口抖动（vivo 热点 ap0 与 wlan0 共存，01:36:05 `ifaces=ap0…` 为证）；
② 相机 AP 空闲/单客户端策略；③ 建链后命令突发触发相机侧重启 PTP 服务。
三者都需要新证据区分（见 §5），**都不指向报文内容**。

**不是切入点**：GUID / clientName / OpenSession 参数 / ConfirmHost 参数 / 补发 CloseSession ——
无任何证据，且动它们直接威胁已跑通的 AP 链（红线）。

## 4. 修复方案与风险（任务 4）

| 方案 | 内容 | 状态 | 风险 |
|---|---|---|---|
| R1 | 注册发现 `ptpConfirm=false`（TCP 筛探）+ 早退 | 已落地（FR-31③④），真机待验 | 休眠相机可能进候选 → 注册 init 超时（有明确文案，可重试） |
| R2 | reason=1 冷却 ≥35s、单向导会话注册 init ≤2 次 | 待拍板 | 用户连点时反馈变「冷却中」文案；误冷却会拉长可注册窗口 |
| R3 | 增 `ptp_tx`/`ptp_rx` 事件（opcode+respcode+txId+通道，**不含 payload**），覆盖注册全程与建链后 15s；AP 会话期 1s 粒度 `net_ifaces` 采样 | 待拍板 | 日志环增量（采样+闸门可控）；不改协议行为，零功能风险 |
| R4 | 复现时同步录相机屏幕 + 手机侧 tcpdump（15740） | 待用户配合 | 无代码风险；tcpdump 需 root 或 PC 端镜像，二选一 |
| 不做 | 改任何报文内容字段、teardown 补 CloseSession、动 keepalive/Pong 时序 | 否决 | 动已跑通链路，违反红线且无证据支持 |

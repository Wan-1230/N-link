# 非上网热点被系统回收：AP 连接「开关定生死」根因与修复方案（2026-10-02）

> 分级：`已验证` = 代码/日志/dex 三向可证；`推断待验证` = 最省假设；`据外部资料` = AOSP/OEM 行为，高置信但非本机实测。
> 触发线索（用户原话）：AP 模式「WiFi 始终开启」开 = 一次成功；关 = 反复失败；部分设备无此开关 = 至今连不上。
> 日志：`n-link_logs_1790911140153.txt`（用户本机 V2509A / Android 16 / 开关=关）。
> 竞品 dex：ZDROP_1.0.257、ZRelay-3.0.76、影犀（/tmp/re32 解包检索）。

（= 系统解除关联或关射频，非相机单侧关服务——相机若关 AP，手机侧表现相同但「WiFi 始终开启」开关不应能阻止它）；
开关=开时同流程零掉线（用户对照实验）。

## 2. 根因（已验证链）

1. **我们的网络请求持不住这张网**：`StaNetworkRequester.acquire()` 的请求为
   `Builder().addTransportType(TRANSPORT_WIFI).build()`。默认请求含 `NET_CAPABILITY_INTERNET`；
   相机热点无互联网、验证失败后系统会剥掉该 capability（据外部资料，AOSP ConnectivityService 行为）
   → 我们的请求**永远匹配不上相机 AP** → 不构成「持有」。
2. **AP 模式走快路径，连请求都不注册**：`acquire()` 的 `findMatchingWifi` 命中即 return，
   `releaseCallbackOnly()` 已先执行且不再注册 → 会话期间**零 NetworkRequest 在册**。
3. **AOSP 回收规则**（据外部资料）：非默认网络（无互联网的 WiFi 永远不是默认，蜂窝才是）
   且**无任何 app 请求持有**时，ConnectivityService 会在宽限后 tear down → wlan0 消失。
   宽限时长随 ROM/负载变化 → 日志里 8.3s / 92s 两种死法同源。
4. **竞品对照（已验证 dex 检索）**：ZDROP / ZRelay-3.0.76 / 影犀 三家均为
   `requestNetwork` + `removeCapability` + `createWifiLock`（ZDROP/影犀 另有 `bindProcessToNetwork`）。
   `removeCapability(NET_CAPABILITY_INTERNET)` 即 local-only 请求标准写法：匹配**未验证**网络并使其
   在册期间不被回收 —— 正是我们缺的那一环。
5. **开关的真实身份**：「WiFi 始终开启」= 系统侧「不因无互联网/省电而回收 WLAN」的总闸。
   开 = 系统不回收 → 掩盖了 1/2 的缺陷；关或 ROM 无此闸 = 缺陷裸露 → 群友「至今无法连接」。
   故该开关**不是根因而是掩码**；根因是持有缺失。相机固件差异只影响 AP 重开周期（~45-60s），
   不影响掉线本身（死亡发生在活流量期间，否证相机省电定时器）。

## 3. 受影响范围

| 维度 | 结论 |
|---|---|
| 相机 | **全部**尼康 AP 模式机型（AP 一律无互联网）；与固件版本无关 |
| 手机 | 所有 Android（AOSP 回收规则普适）；OEM WLAN 助理/智能切换会**加速**踢除 |
| 「开关」可得性 | 因 ROM 而异：部分 vivo/OriginOS、旧版 EMUI 有等价项；多数新 ROM 已移除或深埋 → 无开关用户无自救手段 |
| 我们自己的设备 | 同样受影响（本日志即开关=关的真机）；靠重试运气与自动恢复部分掩盖 |
| 不受影响路径 | USB、BLE、STA 路由器模式中有互联网验证的 WiFi（请求可匹配，持有生效） |

## 4. 修复方案（改动位置 / 核心逻辑 / 关键处理）

**C1（核心修复，闸门 `v33_local_only_request` 默认开）** — `StaNetworkRequester.acquire()`：
请求构造加 `.removeCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET)`。
local-only 请求匹配未验证 WiFi → 在册期间系统保持网络 → 会话不掉线。
关键处理：① 匹配集合变为超集（含无互联网网），**子网过滤 `covers()` 与 FR-20 返回 null 的判据不变**，
绑网决策不受影响；② 释放语义不变（`release()`/`releaseCallbackOnly()` 原样），持有生命周期=会话生命周期。

**C2（AP 快路径补持有）** — 同文件：快路径命中后**仍注册**同一 local-only 请求+回调再返回
（现状是先 `releaseCallbackOnly()` 后裸 return）。关键处理：保持 FIX-3 不变式
「held 非空 ⇔ 回调在册」；重复进入 acquire 时先释放旧回调的现状逻辑正好复用。

**C3（可观测性，闸门 `v32_link_diag` 复用）** — 注册/回调处补事件：
`net_req caps=local-only`、`onAvailable/onLost` 带 `validated=`/`internet=` capability 位。
下一轮真机日志可直接验证「持有生效」：会话期不应再出现 `network_lost`（除非相机真关 AP）。

**C4（兼容兜底，纯 UI/文案，零链路改动）** — `assets/compat/rom_rules.json` + `PreflightGate`：
新增 vivo/小米/OPPO/三星/华为 的「WLAN 助理 / 智能切换 / 自适应连接」关闭指引条目；
并加触发条件：CONNECTED 态 3 分钟内 ≥2 次 `network_lost` 且 C1/C2 已在册 → 弹一次性指引卡
（覆盖「OEM 连持有请求也杀」的极端 ROM）。深链沿用既有 `Settings.ACTION_WIFI_SETTINGS` 机制。

**C5（不做，记录否决）** — `setWifiEnabled(true)` 看门狗、写 `Settings.Global` 休眠策略：
需敏感权限/反射，OEM 行为不一，风险大于收益；C1/C2 是系统正规 API 的正解。

## 5. 验证与回归建议

| 场景 | 期望 | 判据（导出日志） |
|---|---|---|
| 开关=关 + C1/C2 包，AP 连上后监看 5min | 不掉线 | `sta_ifaces` 全程含 wlan0；无 `network_lost` |
| 开关=关，会话中手动关相机 AP | 掉线后 AP 重开即自动恢复 | `network_lost` → `sta_ok` 间隔 ≈ 相机重开周期 |
| 开关=开 回归 | 与现版一致 | 建链耗时分布不劣化（p50 ≈ 4s） |
| STA 路由器模式回归 | 不受影响 | local-only 为超集匹配，子网过滤照旧；`conn_result reason=ok` |
| 扫描回归 | 不受影响 | scan 的 acquire(null,3s) 快路径行为不变（C2 仅补注册） |
| 闸门关回归 | 与旧包逐位一致 | `v33_local_only_request=false` 时请求构造回旧式 |
| USB/BLE | 零触碰 | 本轮不改其代码路径 |

回归红线：C1/C2 只改「请求的 capability 集合 + 快路径是否注册」，不改绑网、子网判据、
退避、状态机；闸门关 = 旧行为。现有可用路径（用户开关=开时的 AP、STA、USB）不被触碰语义。

## 7. 增补：相机端观察修正因果方向（2026-10-02 用户回证）

用户目视：AP 连上后**相机端**显示「无法连接」并**由相机关闭热点**；非手机主动断联。
修正后的因果链：手机系统对无互联网热点的链路层处置（回收 / deauth / 省电不响应，ROM 而异）
→ 相机感知客户端异常 → 相机显示「无法连接」并按自身策略关 AP → 手机 wlan0 失 IP
（日志 `network_lost` / ifaces 消失为其下游表现）。

支持该方向的三条依据：
1. 开关翻转结果但改不了 PTP 字节序列 → 触发源必在手机 WLAN 策略层，不在相机对我们报文的判定；
2. 死亡发生在活流量期间 → 否证相机省电/待机定时器；
3. 时序「PTP 通道先死、wlan0 40ms~1s 内消失」与链路层事件在先兼容。

仍开放的分叉（不阻塞落地，C1/C2 对两支均有效）：手机侧手法是 deauth/回收，还是 WLAN
省电不响应相机 ARP/保活致相机超时。判别法：C3 诊断 + 相机屏幕录像同窗对照 ——
掉线前 wlan0 仍在而相机已判失败 = 省电方向；wlan0 先消失 = deauth/回收方向。

# N-Link 指标口径 v2.5（FR-01）

> 这份文档是**代码的说明书**，不是规划：`app/src/main/java/com/nikonlink/app/shared/metrics/BaselineMetrics.kt`
> 里的常量与本文件一一对应，改一处必须改另一处。
> 目的：让「这次连接变快了」这类话**必须带数字，且数字有唯一算法**，否则等于没说。
> 采集**全部在本机**：不上传、无第三方 SDK、无账号关联（PRD v2.5 §1.3 已裁定不做崩溃率与 ANR 上报）。

导出入口：**设置 → 导出日志**（`SettingsFragment.logExportLauncher`）。导出文本的第一段就是下面三项基线，
后面接原始日志环（3 × 512KB）。基线的原始记录同时以 `metric_conn` / `metric_transfer` / `metric_lv` 行写进日志环，
所以**进程内百分比重启即清零，但历史行仍可事后重算**。

## 1. 连接分阶段耗时

| 项 | 口径 | 代码位置 |
|---|---|---|
| 一次「尝试」 | 从 `ConnFunnel.begin()` 到 `finish()` 收口；被新请求顶掉的记 `superseded`，**不算成功也不算失败** | `ConnFunnel.kt:140,174` |
| 总耗时 `totalMs` | `finishedAt - startedAt`（挂钟，含用户在看弹窗的时间） | `Attempt.durationMs` |
| 阶段耗时 | **相邻两个阶段的时间差**，即该阶段自身耗时；同一阶段被重访（重试）时**取最后一次** | `ConnFunnel.stageGaps()` |
| 单独出百分位的阶段 | **只有四个**：`DISCOVER`（发现相机）、`TCP`（15740 建链）、`HANDSHAKE`（PTP 握手）、`FIRST_COMMAND`（首条命令）。其余阶段（预检、加入热点、路由绑定）只进总耗时，不进阶段表 | `ConnFunnel.MEASURED_STAGES` |
| 按通道分组 | `channel` 原样分组（`WiFi/AP`、`WiFi/STA`、`USB`、`BLE…`），**不合并** | `render()` |
| 窗口 | 进程内最近 **200** 条 | `BaselineMetrics.CONN_LIMIT` |
| 结果分布 | 按 `Reason.code` 计数并给百分比；码值只增不改（既有契约） | `ConnFunnel.Reason` |

**百分位算法：最近秩法（nearest-rank，不插值）**。秩 = `ceil(p × n)`，取升序后第 秩 个样本。
20 个样本时 p50 = 第 10 个、p95 = 第 19 个。选它是因为**样本量小**，插值会造出样本里根本不存在的数，
而我们要的是「拿一次真机数据能复现同一个数」。

## 2. 传输速率与失败分布

| 项 | 口径 |
|---|---|
| 一个样本 | **单个对象**从发出取数到落终态：`bytes = CameraFile.size`（机身声明值）、`elapsedMs` 实测 |
| 速率 | `MB/s = bytes / 1048576 / (elapsedMs / 1000)`；`elapsedMs ≤ 0` 记 0（不跳过，避免出现无分母的漂亮数） |
| 计入百分位 | **只有 `outcome = ok`** 的样本进 p50/p95；失败样本只进结果分布 |
| 结果桶 | `ok` / `incomplete`（字节数没凑齐）/ `storage`（保存失败）/ `error:<异常类名>` |
| 不计入 | ① 「相机未连接」这类**发起前**就返回的（不是一次传输）；② 用户取消（`CancellationException` 直接上抛） |
| 窗口 | 进程内最近 **500** 条 | `BaselineMetrics.TRANSFER_LIMIT` |
| 与通知栏的关系 | 批量完成通知里的 `MB/s` 是**整批合计**（`notifyBatchCompleted`），与本表**逐对象**口径不同，两者不可互相校验，别再混着引用 |

## 3. 监看掉帧率

| 项 | 口径 | 代码位置 |
|---|---|---|
| 一轮（round） | 取帧循环跑一次 = 一次，**无论成功或失败** | `LiveViewManager.startFrameLoop()` 的间隔控制点 |
| 超轮（late） | 该轮 `elapsed ≥ 66ms`，即这一帧把下一帧的预算吃掉了 | `BaselineMetrics.LV_TARGET_INTERVAL_MS` |
| 掉帧率 | `超轮 / 总轮次 × 100%`（**不是**「丢帧数/应有帧数」：我们无法知道机身该出多少帧，只知道自己的节拍有没有超） | `lvDropRate()` |
| 交付帧 | `_latestFrame.tryEmit(frame)` **返回 true** 才计（该流是 `extraBufferCapacity=2` 的 SharedFlow，订阅方跟不上时会失败）；界面右上角的 `fps` 用的是既有 `frameCount`，**两者在缓冲满时会不一致**，以本表为准 | `LiveViewManager.kt:509` |
| 失败帧 | 空帧 / 超时 / 异常进入 `handleFrameFailure` 的次数 | `LiveViewManager.kt:596` |
| 有效帧率 | `交付帧 / 会话时长`，在 `metric_lv` 行里给 `fps=` | `lvSessionEnded()` |
| 会话边界 | 从第一次 `startFrameLoop()` 到 `stopLiveView()` / `stopWithError()` / 链路死亡任一点；就地重启码流**不**重置会话 | `lvSessionStarted()` 幂等 |

⚠ **FR-12（帧率自适应与质量阶梯）会改变本节分母**：一旦目标间隔不再是常数 66ms，
`late` 必须改成与该轮的**实际目标**比较，而不是常量。届时本文档与本表必须同步改，
并把该常量从 `BaselineMetrics` 移到 FR-12 的阶梯定义里。

## 4. 导出内容的边界（脱敏声明）

导出文本**包含**：机型 `Build.MODEL`、ROM 家族、通道名、阶段与总耗时、对象字节数、失败原因码、监看轮次统计。

导出文本**不包含**：照片/视频的文件名与路径、相机序列号与固件版本、WiFi SSID/BSSID、IP 与 MAC、
GPS 位置、任何账号或设备唯一标识。（`download_done` 日志行历史上带 `path=` 字段，
**它是原始日志的一部分，不是基线的一部分**；是否从日志里也去掉属 FR-08d 的判定，本文只声明基线块的边界。）

## 5. 这三项数字用来回答什么

1. 连接：「Z6III + WiFi AP 首连 p95 是多少、死在哪个阶段」 —— FR-02/06/07 的对照物。
2. 传输：「千张卡库下逐对象速率分布、>2GB 的成功率」 —— FR-03/05 的对照物。
3. 监看：「弱链路下掉帧率与断连的取舍」 —— FR-12 的对照物。

没有这三项，PRD 里「下降 ≥30%」这类目标就无法验收（PRD §六 的全部目标都以本文为分母）。

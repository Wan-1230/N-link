## §一 本版唯一硬约束：三链路冻结区

用户红线：**不得修改已跑通的 AP / STA / USB 三条连接链路**。本节把它翻译成可执行的判据，而不是口号。

### 1.1 冻结文件清单（改这些 = 违约，必须先解除冻结）

| 链路 | 冻结文件（相对路径） |
|---|---|
| AP | `app/src/main/java/com/nikonlink/app/device/ap/ApConnectionService.kt`、`…/device/wifi_ap/ApGatewayResolver.kt`、`…/device/wifi-ap/WifiManager.kt` |
| STA | `…/device/wifi_sta/StaNetworkRequester.kt`、`…/device/wifi_sta/WifiNetworkMonitor.kt`、`…/device/wifi-sta/WifiScanner.kt` |
| USB | `…/device/usb/UsbPtpManager.kt`、`…/device/usb/UsbPtpTransport.kt`、`…/device/usb/UsbPtpProtocol.kt` |
| 共享 | `…/device/connect/ConnectionManager.kt`、`ConnectionStateMachine.kt`、`PreflightGate.kt`、`ConnFunnel.kt`、`ConnFlags.kt`、`…/device/ptp/PtpSessionManager.kt`、`app/src/main/java/com/camerakit/**`（PTP/IP 引擎整体） |

### 1.2 允许 / 禁止的判据（新功能怎么碰连接才不算违约）

| 动作 | 判定 | 依据 |
|---|---|---|
| 在**已建立的会话上**新增一次操作码调用（不改握手、不改时序、不改重试、不改状态机、不改网络绑定） | ✅ **允许**，但必须独立闸门 + 失败即静默降级 | 这是"使用链路"，不是"修改链路" |
| 修改任一见习 1.1 文件的**任何一行**，含注释 | ❌ **禁止**，除非解除冻结并同批跑完三链路回归 | 冻结的意义在于回归面归零 |
| 只读复用已有能力（会话对象、存储列表、缩略图通道） | ✅ 允许 | 无写侧副作用 |
| 新增 Android 侧依赖（图片库、色彩库、PDF 等） | ❌ 禁止 | 与「不引外部资源 / 自研解码链」的项目约定冲突（`PRODUCT.md` 明确禁区） |

## §二 需求池

FR-50 起为本版新增功能；历史未竟项一律用 `BK-` 独立序列承接（理由见 §2.2 开头的编号规则，**不可占用 `FR-01~FR-38`**）。**`FR-39~FR-49` 段留白**，因为代码已引用到 `FR-38`、且并行会话可能正在占用后续编号。

### 2.1 本版新增（四个功能）

#### FR-50 水印相框（输出装饰层）`[未]` — 优先级 **P0**

- **落到的闸门格**：S7 / P4（带信息分享是传播面）。
- **现状（已验证）**：全仓 `水印` / `watermark` **零命中**；把文字画进位图的能力**已有先例**（`ArcDialView.kt:129`、`TickRulerView.kt:282` 的 `Canvas.drawText`）；EXIF 通道已有（`PreviewShareExporter.kt:47-61` `EXIF_COPY_TAGS`、`:180-184` `copyExif()`）。
- **技术路径**：在**导出链**上做 Canvas 合成，不新建渲染路径。挂载点两个，必须都接：
  1. `PreviewShareExporter.kt:81 export()` / `:114 exportOriginalUri()` —— 分享；
  2. `TransferManager.kt:1604 saveFileToMediaStore()` —— 存系统相册。
- **模板制**：本版交付 **5 个自产模板族**（纯白留白 / 纯黑留白 / 细描边 / 底部信息条 / 参数注脚），参数化 spec 描述（外留白比例、内衬、圆角、字串槽位 = 机型 / 焦距 / 光圈 / 快门 / ISO / 日期 / 自定义文字）。**素材全部自产，不内置任何外部模板文件与位图。**
  - 两层能力要一次设计、分开交付：**「仅信息条」（不加框、只叠文字）** 与 **「整幅相框（改画布尺寸）」** 共用同一套 spec，只差是否扩边。第一版把两层都留接口，实装先从简的那层起。
- **失败态必须分类，不许一句"处理失败"带过**：`PRODUCT.md` 已定人格 —— 错误信息写「原因 + 怎么办」。本条至少有四类各自不同的下一步：① 模板文件缺失/损坏 → 引导重置模板目录；② 源图无法解码 → 说明是原图问题，可跳过继续批量；③ 合成成功但写入相册被拒（权限 / 存储空间）→ 直达系统设置；④ 批量中途失败 → 明确「已出 N/M 张」并可续。
- **硬要求**：默认**关闭**；开启时**另存为新图**，覆盖原图需二次确认（沿用 `docs/PRD-N-Link-AI修图.md` §3.1 已定的导出口径，原件归档后该口径迁入本节）。
- **EXIF 规则**：合成后必须重算 `ImageWidth/ImageHeight`，且 `EXIF_COPY_TAGS` 白名单**不得为省事而扩大**（搬运不等于改写，口径见 `docs/连接与元数据可靠性专项-v1.md` §2.2「允许的清理 vs 禁止的改写」，原件归档后规则本身继续生效）。
- **成本**：**M**（1.5 人日）。**风险**：低，纯客户端，不碰连接、不碰监看渲染链。
- **闸门**：新增 `UiFlags.EXPORT_FRAME`，默认 false，关闸 = 现行为逐位不变。

#### FR-51 相册实时 LUT `[未]` — 优先级 **P0**（分两档，先做预览档）

- **落到的闸门格**：S7 / **P3**（创作者在挑片阶段判色）。
- **关键取舍 —— 这条为什么现在能做**：旧规划把「LUT」和「监看帧率阶梯」绑在一起判死（同一条渲染链不能同时改两处）。**本条刻意只做相册，不碰监看链** —— 相册走的是自研解码链（`ThumbnailCache.kt:204,210` 后台 `BitmapFactory.decodeByteArray` → 主线程 `setImageBitmap`，`PhotoGridAdapter.kt:48`），与监看链（`LvFrameDecoder` → `ImageView.setImageBitmap`）**是两条链**。互锁解除。
- **两档划分**：
  - **FR-51a 预览套色**（本版做）：网格缩略图 + 大图预览套 LUT，**只改显示，不改文件**。
  - **FR-51b 烘焙导出**（P1，排在 FR-51a 之后）：把套色结果写进导出文件，与 FR-50 共用同一条合成链，**一次做完不改两遍**。
- **可直接复用的自有先例（这是本条成本可控的真正原因）**：
  - `liveview/PseudoColorLut.kt:19-45` —— 已是「**256 项亮度 → ARGB 反查表**」形态、且**纯 JVM 可单测**，LUT 的数据结构与查表骨架与它同构，解析器与单测可平移；
  - 相册侧是 `ImageView` 体系（`PreviewActivity.kt`、`PreviewZoomImageView.kt`），**可挂点明确**；
  - CPU 像素处理先例：`GlassBackdrop.kt:436,451`。
- **技术路径（受 minSdk 卡死，必须主 CPU + GPU 加速双路）**：`app/build.gradle.kts:22` `minSdk = 29`。
  - API 31+：`RenderEffect`；API 33+：`RuntimeShader`/AGSL —— 现两处在代码里**仅存于注释**（`GlassBackdrop.kt:24,640`、`UiFlags.kt:227,306`），即**能力未落地**；
  - 因此**主路径必须是 CPU**：`.cube` 解析 + 三线性插值查表；GPU 三维纹理路径只作为 API 33+ 的**加速覆盖**。
  - **必须内置自动降级**：`.cube` 的 `LUT_3D_SIZE` 可能超过 GPU 三维纹理上限，**超限即回退 CPU 并保证结果一致**，不许出现"高端机一个色、低端机另一个色"。
  - **参数契约按四件设计**：启用 / 强度 / 旁路（用于前后对比） / 尺寸，强度与旁路是「实时」二字的最低要求，缺一个就退化成滤镜。
- **素材与版权（阻塞级）**：外部授权 `.cube` 素材包**一律不得内置**（旧规划已判死，理由为版权，条目见 `docs/archive/PRD-N-Link-v2.7-产品规划.md` §七 N4）。本版只做：① 自产少量基础 LUT；② 让用户导入**自有** `.cube` 文件（公开格式，解析器自研，不引第三方库）。
- **不得复用的开关**：**不要**挂到 `TONE_TOOLS`（`UiFlags.kt:107`）。那是监看侧伪彩/波形总闸，其开闸判据挂在 **BK-12 的真机数据**上（要到 M5 才有结论）；相册 LUT 挂它会把自己锁死在一个不相干的真机结论上。新增独立闸 `UiFlags.ALBUM_LUT`。
- **成本**：FR-51a **L**（≈4 人日，含解析器与 CPU 套色）。**风险**：中 —— 全仓 `ColorMatrix` 目前**零命中**，色彩处理是新建面；但纯客户端，可整体回退。

#### FR-52 尼康云创预设导入相机 `[未][机]` — 优先级 **P2**（本版**不排产品实现**，只排探测）

- **落到的闸门格**：P2/P3（机身色彩配方）+ S2。
- **先厘清一件事，否则会被误判为「翻旧案」**：`docs/archive/PRD-N-Link-v0.1.3-问题修复.md` §5 已裁定**不接入尼康云创云端 API**，阻塞点是 B1 无公开 API / B2 无第三方 OAuth 客户端注册入口 / B3 违反 ToS。
  **本条与该结论不冲突，也不推翻它。** 本条做的是「**用户自有预设文件 → 本机 → 相机**」的本地写入：**不调用任何云服务接口、不复用任何第一方 client_id、不做任何认证、不碰凭据**。旧结论继续有效，云端 API 接入仍是**不做**。
- **现状（已验证，这是本条最大的成本来源）**：**全仓 PTP 对象写侧零实现** —— `0x100C` / `0x100D` / `SendObject` / `AddObject` / `0x1022` 在 `app/src` 与 `nikon-conn-kit/` 全部**零命中**（含 `.kt` 与 `.java`）；操作码表止于 `OP_DELETE_OBJECT = 0x100B`（`…/device/ptp/PtpProtocol.kt:18 object PtpConstants`，尼康段 `:85-127`）。
- **但有一条已验证的降成本事实**：**属性写侧已经通了** —— `OP_SET_DEVICE_PROP_VALUE = 0x1016` 在 `com/camerakit/ptp/PtpConsts.kt:24`、`PtpSessionAppExt.kt:22`、`ApEngineBridge.kt:162`、`PtpSessionManager.kt:1018`、`UsbPtpManager.kt:1179` 均已在用，即「带数据阶段的命令收发」骨架存在，`PtpSession.transact` 是明确的扩展点（`nikon-conn-kit/` 是它的同源工程）。**所以本条不是从零起盘，是从"能写属性"跨到"能写对象"。**

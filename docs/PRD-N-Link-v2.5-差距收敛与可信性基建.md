## 一、为什么是这一版

### 1.1 六条压力

| # | 压力 | 依据 |
|---|---|---|
| 1 | **地基债已被竞品抹平**：STA 超时缺失、大库相册、>2GB 正确性、主机注册不可解释——这几项我们靠"能用"糊过去，ZDROP / ZRelay 已用「双通道 + 逐阶段重试 + 可见拒绝原因」把它做成基线 | 竞品分析 §2.3、§2.4 |
| 2 | **免费的官方专业方案在挤压我们的核心卖点**：影速传 NX MobileAir 1.6.0 起专业档**免费**，而它做的是 USB 直连 RAW + 4G/5G 推送——正对着我们「USB + 原图」的说法 | 竞品分析 §2.2、§7 |
| 3 | **同路人在快速逼近**：帧澈 ZENCHE（MIT）已有可调帧率、RGB 分量波形、矢量示波、伪彩、斑马、峰值对焦、FTP/HTTP/WebDAV 收件箱；虽 2026-08-22 后无提交，但能力面差距是可见的 | 竞品分析 §2.7 |
| 4 | **一个带日期的窗口**：尼康影像馆（IMAGE SPACE）中国版 **2026-10-15 终止**，接替的 Imaging Cloud 只覆盖 Z6III/Z5II/Zf/Z50II 四台。被官方弃养的用户需要「本机落盘 + 不经云端」的路径，这正是我们的结构性位置 | 竞品分析 §2.1、§8 |
| 5 | **可信性正在成为隐性门槛**：ZRelay 用「重连评分 + 可见拒绝原因 + 服务端推送 camera-rules」把"我们内部靠实测积累的兼容知识"产品化了；我们把兼容矩阵落成了 `assets/compat/rom_rules.json`，但**加新机型仍要发版** | 竞品分析 §2.4；本仓库 `CompatRules.kt` |
| 6 | **Android 平台独占窗口正在关闭（2026-09-21 新增）**：影控台（iOS ¥148 买断 + Lite 免费 + Lite Plus ¥9.9/月）已把「监看工具一整套 + 1:N 群组 + 相机端标记速传 + 按 Expeed 代际分层」做成成品，10 周更 21 版，**Android 版正在内测**。它带来的不只是功能竞争，还有**「尼康 App 应该收费」的心智竞争** | 竞品分析 §2.11（App Store 一手）、§8 机会窗口 7 |

> 压力 4 是本版唯一的**硬日期**，因此 v2.5.0 必须在 2026-10-15 之前发布（§七）。
> 压力 6 与压力 4 方向相反但同样紧迫：它**不给出交付日期，只给出「本文的优先级排序不能再靠后」**——所以我们**不**因它临时插入监看类功能，而是照 §七 把基线与可信性先立住（这才是它真正改变的判断）。

### 1.2 本期目标（三条，可验收）

- **T1 把地基债还掉**：STA 超时、大库相册、>2GB、主机注册四件事做到"失败能解释、成功有基线"。
- **T2 把可信性做成产品能力**：版本/渠道/包校验值可见，诊断可导出，隐私授权有统一范式（复用 v2.3.1 已上线的快门云端授权）。
- **T3 抢影像馆停服窗口**：在 10-15 前给出「从尼康云迁出到本机」的明确路径与对外说法。

## 二、现状基线

### 2.1 「已实现」的三档定义（本版本说适用所有盘点）

| 档 | 含义 | 本期是否算完成 |
|---|---|---|
| **L1 编译+单测过** | 代码在、单测绿，未在真机跑过 | ✗ 不算 |
| **L2 真机跑过单次** | 某个机型/某台手机上成功过一次 | △ 部分 |
| **L3 真机矩阵通过 + 有回归脚本** | §九 的组合矩阵有记录 | ✓ 算 |

**结论：本仓库绝大多数功能停在 L1。** 因此 v2.5 的第一批产出不是新功能，而是基线与回归能力。

## 三、优先级判据与总表

### 3.1 判据（沿用项目既有裁定，不另立标准）

1. 影响"能不能连上、能不能传完"的排最前；影响"看着先爽"的排后。
2. 触碰曾被真机修过的核心区（PTP 事务层、下载队列、连接状态机）的，必须带闸门 + 真机矩阵，不许静默改。
3. 一切新行为可回退：有闸门的写闸门，没闸门的说明为什么不需要。
4. 有日期的机会优先于同等工作量的功能（影像馆 10-15）。

## 四、功能需求

> 每个 FR 固定六段：**现状证据 / 目标 / 范围与边界 / 验收标准 / 闸门 / 风险**。写不出「验收」或「闸门」的条目不配进本期。

### A 批次（P0）

#### FR-01 连接与传输指标基线
- **现状**：所有"变快了/更稳了"的说法都没有对照物；v2.2 §7.4 提过 p50/p95 但从未落地。
- **目标**：先把量打出来，再谈优化。定义并采集：连接各阶段耗时（发现/TCP/握手/首帧）、传输 MB/s 与失败原因分布、监看掉帧率。
- **范围与边界**：只做本地统计与导出，**不上传任何遥测**；不含崩溃率（见 §1.3）。落点为现有漏斗 `ConnFunnel`，不新建埋点框架。
- **验收**：① 一台真机能导出一次完整会话的分阶段耗时；② 三个指标的口径写进文档且与代码常量一致；③ 导出内容脱敏声明落地（呼应 v2.2 §7.2）。
- **闸门**：不需要（纯采集，不改变行为）。
- **风险**：采集本身引入日志噪声 → 采样率与开关由 FR-08 的诊断导出统一管。

#### FR-02 STA 侧网络请求补齐超时与生命周期
- **现状**：STA 路径存在无超时与不可取消的网络等待，失败时原因码不可解释（v2.2 §5.2）。
- **目标**：每个 STA 侧网络动作都有显式超时、可取消、失败原因唯一。
- **边界**：**不**引入 OkHttp；沿用现有 socket 与协程取消语义。不碰 P0 的事务层。
- **验收**：① 拔掉相机 WiFi 后，任一路径在既定超时内失败并给出对应原因码，不出现"永久转圈"；② 新增单测覆盖三条路径的超时分支。
- **闸门**：`v25_sta_timeouts`。
- **风险**：超时设短会误杀慢速机身 → 超时值进兼容矩阵（FR-14）按机型可调。

#### FR-03 大库相册首屏与增量入册
- **现状**：大库首屏与增量刷新仍慢（v2.2/竞品 GAP）；**注意**：当前的"分页保持"是刻意设计，防止列表跳回顶部（`TransferViewModel.kt` 注释与 `TransferFragment.kt:133`）。
- **目标**：千张级卡库首屏可见时间下降，且新照片增量入册不打断当前浏览位置。
- **边界**：**禁止**为提速而回退防跳底逻辑——这是踩过的坑。分页协议改造优先于渲染改造。
- **验收**：① 1000+ 张卡库首屏 p50 < 基线值 −30%；② 下载中收到新照片事件，列表位置不跳动；③ 与"已下载/未下载"筛选联动无回归。
- **闸门**：`v25_album_incr`。
- **风险**：`0x9805` MTP 批量属性并非所有机身支持 → 保留逐对象回退。

#### FR-04 数据期抽干 event 通道（⚠ 触碰核心区）
- **现状**：大文件传输期间不读 event socket，机身事件饿死（v2.2 §2.5），是周期性掉线的根因假设之一。
- **目标**：数据阶段持续抽干 event，事件不再积压。
- **边界**：只动 `PtpSessionManager` 的读取调度，**不改**事务串行锁的语义；不改下载队列状态机。
- **验收**：① 真机传输 20 张 RAW 期间 `CaptureComplete` 等事件不再延迟到传完才到达；② 现有掉线回归用例不劣化；③ 无双通道并发写导致的乱序。
- **闸门**：`v25_event_drain`，**默认关**（核心区，先灰度）。
- **风险**：这是本版最高风险项。若真机出现任何新的掉线模式，直接关闸门回到现状。

#### FR-05 >2GB 文件传输正确性（⚠ 触碰核心区）
- **现状**：断点续传 offset 用 `Int`，>2GB 会溢出；超限时退化为整对象重下（`TransferManager.kt:747-753`）。
- **目标**：>2GB 视频/RAW 包能续传，不静默重来。
- **边界**：不改小文件路径；不引入 64 位厂商扩展（`0x9431` 等，需 FR-15 结论）。
- **验收**：① 单测覆盖 offset 边界（2GB±1）；② 真机中断后恢复不重复传输已完成部分；③ 失败原因码可区分"不支持续传"与"链路断"。
- **闸门**：`v25_partial64`。
- **风险**：机身对大 offset 的 `GetPartialObject` 行为不一致 → 先探测后启用。

#### FR-06 主机注册可解释化
- **现状**：发出注册命令即置成功标志，且等待时长写死 8.5s。
- **目标**：以机身实际状态（事件或回读）判定注册结果，失败给出可执行指引。
- **边界**：不改 STA/AP 选择策略；不改 `0x952B/0x935A` 的调用方式（其正确性由 FR-15 复核）。
- **验收**：① 未注册/注册被拒/注册成功三态在 UI 上可区分；② 取消固定 8.5s，改为事件驱动 + 上限保护。
- **闸门**：`v25_hostreg_verify`。
- **风险**：部分机身不发对应事件 → 超时回落到旧行为。

#### FR-07 机身唯一客户端争抢的腾挪引导（竞品全无）
- **现状**：机身同时只接受一个 PTP/IP 客户端，SnapBridge 或另一台手机占着就必然失败；我们只报"连接失败"。
- **目标**：识别这类失败并给出**具体**腾挪步骤（去哪、点什么、要不要关蓝牙/WiFi 自动同步）。
- **边界**：纯引导与文案，不改协议行为；不得声称能"踢掉"对方连接。
- **验收**：① 争抢型失败有专属原因码与专属文案；② 文案经真机复现验证（Z50II + 已连 SnapBridge）。
- **闸门**：不需要（只增解释，不改行为）。
- **风险**：误判为争抢会误导用户 → 判定条件保守，宁缺毋滥。

#### FR-08 可信性基建包
- **现状**：用户无法自查"我装的是哪版、下没下错包"；诊断无出口；快门云端授权是项目里**唯一**一处规范化的隐私授权。
- **目标**：把"可信"做成可点开的界面能力。
  - **a** 设置页展示版本 + versionCode + APK 校验值前 8 位 + 发布渠道（GitHub / 夸克 / 百度），与 `version-info.txt` 对照；
  - **b** 失败样本留档与导出（**修 v2.4 自己挖的坑**：现在五处 `delete()` 把证据删了）；
  - **c** 抽出具名化的通用授权组件（照 v2.3.1 快门的 `AppSettings.shutterCloudConsent` 范式），供后续任何"要把用户数据交给第三方"的功能复用；
  - **d** 导出诊断时明确声明包含/不包含哪些字段。
- **边界**：不接任何遥测服务；导出走系统分享，不落第三方。
- **验收**：① 三渠道包都能自证版本与校验值；② 快门解析失败后能真的拉出留档样本（呼应 PRD v2.4 §十）；③ 授权组件被至少一处复用。
- **闸门**：`v25_diag_export`。
- **风险**：导出内容含路径/机型信息 → 脱敏清单进 §8.1 铁律。

#### FR-09 targetSdk 36 升级
- **现状**：`targetSdk = 35`；ZRelay、影犀均已 36。落后不只是数字，Android 16 的行为变更（边到边、权限、后台限制）会逐个咬到 v2.3 遗留的边到边未收口项（`themes.xml:26` 仍有 opt-out）。
- **目标**：升到 36 且无功能回归。
- **边界**：不与 FR-04/05 同期上，避免同时改两处；升级引起的手感问题按项单列。
- **验收**：① 三通道连接、监看、下载、设备页在 16 与 10（minSdk 29）两端各跑一遍；② 边到边不留黑边/遮挡；③ 无新增权限。
- **闸门**：无（构建配置项，回退 = 改回 35 重发）。
- **风险**：本版最容易引发大面积视觉回归的项 → 排在 A 批次最后做。

#### FR-10 快门链路三处收尾
- **现状**：命中第一个能解析的样张就返回（无互验）；多样本一致性、单调性校验未做；真机夹具为空。
- **目标**：把"读对了"与"碰巧读到个数"分开。
- **边界**：不动已上线的解析器结构（`0x8769 → 0x927C`、IFD 枚举、恒等式）；不引入现拍兜底（v2.4 已裁定）。
- **验收**：① 同一机身最新 2–3 张样张互验，不一致时给区间而非单值；② 新拍一张后读数不减；③ 用户投放自拍 NEF+JPEG 切片后，夹具测试从"跳过"变为"通过"。
- **闸门**：`v25_shutter_crosscheck`。
- **风险**：互验要多读样张 → 每次仍只读头部，成本可控。

#### FR-11 影像馆停服承接（硬日期 2026-10-15）
- **现状**：尼康 IMAGE SPACE 中国版将终止，接替方案只覆盖四台机身；被弃养用户的诉求是"照片能落到手机/电脑，不经第三方云"。
- **目标**：在停服前给出明确承接路径与对外说法。
- **边界**：不承诺"导入影像馆历史存档"（我们拿不到其云端数据）；只承接**相机里的照片**这一诉求。
- **验收**：① README 与设置页有一段面向该场景的说明（不夸大）；② 发版物料与更新介绍含此条目；③ 批量落盘与"跳过已下载"在千张级卡库上可用（依赖 FR-03）。
- **闸门**：不需要（文档与文案）。
- **风险**：窗口期一过价值递减 → 与 A 批次同版发，不延后。

### B 批次（P1，v2.5.x 增量，不占 10-15 窗口）

#### FR-12 监看监看帧率自适应与质量阶梯
现状：帧间隔固定 66ms（`LiveViewManager.kt:39`）。目标：按链路质量在阶梯上自适应降/升档，掉帧时优先保连接而非保帧率。验收：弱链路下掉帧率下降且不断连；档位切换有可见提示。闸门 `v25_lv_quality_ladder`。风险：与 FR-04 相互作用，必须等 FR-04 有真机结论。

#### FR-13 影调工具包（伪彩 + RGB 分量波形）
现状：只有亮度直方图，且是进阶开关（默认关）。目标：补齐曝光判断真正需要的**伪彩**与**RGB 分量波形**，直接对位帧澈与影控台（后者已把「LUT + 伪色 + 斑马 + 直方图 + 波形 + 安全区 + 水平仪 + 反挤压」做成 ¥148 买断档的付费理由，竞品分析 §2.11）。验收：① 监看帧率不低于无工具时的 80%；② 开关位置与直方图同级，不进默认铺开的区域；③ 与影控台的差集（**峰值对焦**）明确写进"本期仍不做"，不假装补齐。闸门 `v25_tone_tools`。风险：矢量示波器明确不做（§1.3）；自绘控件成本被低估是此类需求常见坑，先做伪彩。

#### FR-14 兼容矩阵运营与热更
现状：`assets/compat/rom_rules.json` 已数据化，但加机型要发版；ZRelay 用服务端 `/v1/camera-rules` 已验证该路线。目标：只读远程规则覆盖本地资产，失败静默回退。验收：① 断网/404/坏 JSON 三种情况都不影响连接；② 远程版本可见可关；③ 新增一条机型引导不发版即生效。闸门 `v25_rules_remote`（默认关）。风险：任何"可写/可下发指令"的服务端能力都不在本期范围；先只读、先自建最小静态文件。

#### FR-15 私有命令码探测专项（研究项，产出结论不产出功能）
现状：ZTransfer 公开断言我们的 `0x952B/0x935A` 全错，并声称 `0x9838/0x93D4/0x9714/0x9A6C/0x9918` 有效；其仓库无 License，**不可复用其取值**。目标：用真机把这几组码的性质逐条判定（有效/无害/破坏性），产出可引用的结论表。验收：结论表入库并回写 v2.2 §8.2 的 `CameraProfile` 依据。闸门：无（研究项，只在调试通道执行）。风险：探测可能改变机身状态 → 只在用户自备的测试机上、可断电复位的前提下做。

#### FR-16 相机侧「保护标记」选择性传入（对标影控台「速传」，竞品分析 GAP-27）
现状：我们**只读**保护位（`TransferManager.kt:839` 解析 `protectionStatus`），全仓无 `0x101A SetObjectProtectionStatus`（操作码表 `PtpProtocol.kt:48-65` 止于 `0x101B`）；「要传哪几张」只能在手机侧逐个多选。目标：把机内**保护键**当成传输清单——现场按保护，回到 App 一键「只传已保护的」。验收：① 相机里标过保护的张能一次筛出并下载，未标的不进队列；② 若 `0x9805` 批量属性里已含保护位，**不得**退化成逐张 `0x1008`；③ 机身写入能力真机确认前，UI 不出现「取消保护」这类会改变机内状态的动作。闸门 `v25_protect_select`（默认关）。风险：尼康机型对 `0x101A` 的支持面未验证（竞品分析把它标在 ❓）→ **只读筛选先做，零协议风险**；写入另立小项，探测前不承诺。

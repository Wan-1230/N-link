## 一、为什么是这一版

### 1.1 六条压力

| # | 压力 | 依据 |
|---|---|---|
| 1 | **地基债已被竞品抹平**：STA 超时缺失、大库相册、>2GB 正确性、主机注册不可解释——这几项我们靠"能用"糊过去，ZDROP / ZRelay 已用「双通道 + 逐阶段重试 + 可见拒绝原因」把它做成基线 | 竞品分析 §2.3、§2.4 |
| 2 | **免费的官方专业方案在挤压我们的核心卖点**：影速传 NX MobileAir 1.6.0 起专业档**免费**，而它做的是 USB 直连 RAW + 4G/5G 推送——正对着我们「USB + 原图」的说法 | 竞品分析 §2.2、§7 |
| 3 | **同路人在快速逼近**：帧澈 ZENCHE（MIT）已有可调帧率、RGB 分量波形、矢量示波、伪彩、斑马、峰值对焦、FTP/HTTP/WebDAV 收件箱；虽 2026-08-22 后无提交，但能力面差距是可见的 | 竞品分析 §2.7 |
| 4 | **一个带日期的窗口**：尼康影像馆（IMAGE SPACE）中国版 **2026-10-15 终止**，接替的 Imaging Cloud 只覆盖 Z6III/Z5II/Zf/Z50II 四台。被官方弃养的用户需要「本机落盘 + 不经云端」的路径，这正是我们的结构性位置 | 竞品分析 §2.1、§8 |
| 5 | **可信性正在成为隐性门槛**：ZRelay 用「重连评分 + 可见拒绝原因 + 服务端推送 camera-rules」把"我们内部靠实测积累的兼容知识"产品化了；我们把兼容矩阵落成了 `assets/compat/rom_rules.json`，但**加新机型仍要发版** | 竞品分析 §2.4；本仓库 `CompatRules.kt` |
| 6 | **Android 平台独占窗口正在关闭（2026-09-21 新增）**：影控台（iOS ¥148 买断 + Lite 免费 + Lite Plus ¥9.9/月）已把「监看工具一整套 + 1:N 群组 + 相机端标记速传 + 按 Expeed 代际分层」做成成品，10 周更 21 版，**Android 版正在内测**。它带来的不只是功能竞争，还有**「尼康 App 应该收费」的心智竞争** | 竞品分析 §2.11（App Store 一手）、§8 机会窗口 7 |

> 压力 4 是本版唯一的**硬日期**，因此 v2.5.0 必须在 2026-10-15 之前发布（§七）。
> 压力 6 与压力 4 方向相反但同样紧迫：它**不给出交付日期，只给出「本文的优先级排序不能再靠后」**——所以我们**不**因它临时插入监看类功能，而是照 §七 把基线与可信性先立住（这才是它真正改变的判断）。

### 1.2 本期目标（三条，可验收）

- **T1 把地基债还掉**：STA 超时、大库相册、>2GB、主机注册四件事做到"失败能解释、成功有基线"。
- **T2 把可信性做成产品能力**：版本/渠道/包校验值可见，诊断可导出，隐私授权有统一范式（复用 v2.3.1 已上线的快门云端授权）。
- **T3 抢影像馆停服窗口**：在 10-15 前给出「从尼康云迁出到本机」的明确路径与对外说法。

## 二、现状基线

### 2.1 「已实现」的三档定义（本版本说适用所有盘点）

| 档 | 含义 | 本期是否算完成 |
|---|---|---|
| **L1 编译+单测过** | 代码在、单测绿，未在真机跑过 | ✗ 不算 |
| **L2 真机跑过单次** | 某个机型/某台手机上成功过一次 | △ 部分 |
| **L3 真机矩阵通过 + 有回归脚本** | §九 的组合矩阵有记录 | ✓ 算 |

### 3.1 判据（沿用项目既有裁定，不另立标准）

1. 影响"能不能连上、能不能传完"的排最前；影响"看着先爽"的排后。
2. 触碰曾被真机修过的核心区（PTP 事务层、下载队列、连接状态机）的，必须带闸门 + 真机矩阵，不许静默改。
3. 一切新行为可回退：有闸门的写闸门，没闸门的说明为什么不需要。

## 四、功能需求

> 每个 FR 固定六段：**现状证据 / 目标 / 范围与边界 / 验收标准 / 闸门 / 风险**。写不出「验收」或「闸门」的条目不配进本期。

### A 批次（P0）

#### FR-01 连接与传输指标基线
- **现状**：所有"变快了/更稳了"的说法都没有对照物；v2.2 §7.4 提过 p50/p95 但从未落地。
- **目标**：先把量打出来，再谈优化。定义并采集：连接各阶段耗时（发现/TCP/握手/首帧）、传输 MB/s 与失败原因分布、监看掉帧率。
- **范围与边界**：只做本地统计与导出，**不上传任何遥测**；不含崩溃率（见 §1.3）。落点为现有漏斗 `ConnFunnel`，不新建埋点框架。
- **验收**：① 一台真机能导出一次完整会话的分阶段耗时；② 三个指标的口径写进文档且与代码常量一致；③ 导出内容脱敏声明落地（呼应 v2.2 §7.2）。
- **闸门**：不需要（纯采集，不改变行为）。
- **风险**：采集本身引入日志噪声 → 采样率与开关由 FR-08 的诊断导出统一管。

#### FR-02 STA 侧网络请求补齐超时与生命周期
- **现状**：**真因已定位（09-21 逐行复核，本文原引的 `StaNetworkRequester.kt:129` 是错的）** —— `PtpSessionManager.kt:259` 在非配对模式给 event 通道 `soTimeout = 0`，相机接了 TCP 却不回 `InitEventAck` 时卡在 `:269` 的阻塞读上；阻塞 read 不是挂起点，上层的 generation 校验根本没有执行机会。次因：`StaNetworkRequester` 用的是无系统超时的两参 `requestNetwork`、`WifiScanner.collectArp` 的 `timeoutMs` 声明了但没用、二段扫把 18s 写死而不看调用方预算。
- **目标**：每个 STA 侧网络动作都有显式超时、可取消、失败原因唯一。
- **边界**：**不**引入 OkHttp；沿用现有 socket 与协程取消语义。不碰 P0 的事务层。
- **验收**：① 拔掉相机 WiFi 后，任一路径在既定超时内失败并给出对应原因码，不出现"永久转圈"；② 新增单测覆盖三条路径的超时分支。
- **闸门**：`v25_sta_timeouts`。
- **风险**：超时设短会误杀慢速机身 → 超时值进兼容矩阵（FR-14）按机型可调。

#### FR-03 大库相册首屏与增量入册
- **现状**：**根因是两头都占**（09-21 复核）——`fetchPhotoListDetailed` 的 `onPage` 给的是**当前这一页**（handle 原始序，与展示的倒序几乎完全逆序），`loadPhotos` 拿它直接整表替换 `_photoList`，于是视口被 DiffUtil 拖走再弹回（`TransferFragment.kt:133` 的防跳底就是为此存在）；v2.3 的解法是 `holdPages` **干脆一页都不发射**，代价退到另一头：**首屏 = 全量耗时**，千张卡库空转十几秒。
- **目标**：千张级卡库首屏可见时间下降，且新照片增量入册不打断当前浏览位置。
- **边界**：**禁止**为提速而回退防跳底逻辑——这是踩过的坑。分页协议改造优先于渲染改造。

#### FR-04 数据期 event 静默被误判死（⚠ 触碰核心区｜**原描述已被证伪，09-24 改写**）
- **现状订正**：本文原写「大文件传输期间不读 event socket，机身事件饿死」——**这句话不成立**。逐行复核：event 通道从会话建立起就有一个独立协程在读（`PtpSessionManager.kt:961` `startEventListener`，于 `:364` 启动），命令通道读 `commandInput`（`:223`）、event 通道读 `eventInput`（`:280`），是**两条 TCP socket**，下载大文件不会占住 event 的读；读取循环也不碰 `commandMutex` / `thumbLane` 任何一把锁。USB 侧同样有常驻轮询（`UsbPtpManager.kt:1117` `startEventPolling`，走 Interrupt IN）。所以按原范围，本项**无事可做**——v2.2 §2.5 记的是监听器出现之前的账。
- **复核挖出的真缺陷**：`PtpPacket.fromStream` 把四种性质完全不同的事塌缩成一个 `null`（对端关闭 / 声明长度荒谬 / 包解不出来），而 `soTimeout` 到期抛的 `SocketTimeoutException` 又分不清"45s 一个字节没来"与"包只读到一半"。于是 event 侧一律 `markLinkError("event_read_timeout")` —— **而同样这种静默在心跳路径是有豁免的**（`:914-921`：`TRANSFER_HEARTBEAT` + `bulkDepth > 0` 时相机静默算正常）。一处豁免一处不豁免，合起来就是"传一张大 RAW 传到自己把链路掐了"，这是目前周期性掉线最像样的假设，替换掉原先那条被证伪的。
- **处理**：读包拆成 `EventStreamPump`（`Idle` 静默 / `Partial` 流错位 / `Closed` 对端关闭 / `BadFrame` 脏帧 / `Unparsable` 跳过 / `IoError` 线断），事件通道按判据分支处置。**只放行 `Idle`**：包读到一半属于流错位，接着读就是把包尾当下一个包头，任何时候都判死。
- **验收**：① 传 ≥60MB 文件期间不再出现 `event_read_timeout` 判死；② 心跳与命令通道的判死路径一字未动（`no_response_xN`、`idle_timeout` 仍在算）；③ 关掉闸门逐支回到 v2.3.2 行为，连 `event_read_timeout` 这个原因码都保留；④ `Partial` / `IoError` 仍判死，不能被"容忍静默"顺带放过（`EventStreamPumpTest` 10 条钉住，其中 3 条专门钉这两支不许漏）。
- **闸门**：`v25_event_silence_hold`，**默认关**（核心区，先灰度）。调试包的「开发选项」里能直接开，不必 adb。
- **风险**：真断链时不再由 event 侧抢先判死，检测延后到命令通道失败或心跳累计 —— 两条都还在，不会永久挂起；`Unparsable` 在闸门开时改为"跳过这一个包继续读"，脏流若持续会有 skipped 计数进日志而不是一声不响地把事件通道关掉（旧实现 `break` 后 `_sessionState` 仍是 CONNECTED，事件从此再也不到，是比误判死更隐蔽的坑）。

#### FR-05 >2GB 文件传输正确性（⚠ 触碰核心区）
- **现状**：**根因不是我们的装箱**（09-24 复核订正）——标准 PTP `GetPartialObject`(0x101B) 的 offset 本身就是 **32 位参数**，文件写到 2GB 之后没有合法 offset 可发；代码已在越界时安全退出续传、改走无 offset 的 `GetObject` 整文件下载（`TransferManager.kt` 的 G10 分支）。真正缺的是"能接着传"，不是"别溢出"。

- **验收**：① **已完成**——边界判定抽成 `ResumePolicy` 纯函数，7 个单测钉住 2GB±1 与"起点为 0 才清档"；③ **已完成**——新增 `DownloadOutcome`（`Complete/BeyondResumeRange/LinkBroken`），"机身续传范围之外"与"链路断了"文案、日志 reason（`no_resume` / `incomplete`）与 FR-01 传输分桶三者同时分开；② **未完成，必须真机**——需要一张 >2GB 的 MOV 与一次可控中断。
- **闸门**：`v25_partial64` —— **本期待实现状态**：64 位路径还没写，闸门不生效；实现时**默认关**（表格里原先登记的"开"是错的，已改）。

#### FR-16 相机侧「保护标记」选择性传入（对标影控台「速传」，竞品分析 GAP-27）
现状：我们**只读**保护位（`TransferManager.kt:869` 解析 `protectionStatus`），全仓无 `0x101A SetObjectProtectionStatus`（操作码表 `PtpProtocol.kt:48-65` 止于 `0x101B`）；「要传哪几张」只能在手机侧逐个多选。目标：把机内**保护键**当成传输清单——现场按保护，回到 App 一键「只传已保护的」。验收：① 相机里标过保护的张能一次筛出并下载，未标的不进队列；② 若 `0x9805` 批量属性里已含保护位，**不得**退化成逐张 `0x1008`；③ 机身写入能力真机确认前，UI 不出现「取消保护」这类会改变机内状态的动作。闸门 `v25_protect_select`（默认关）。风险：尼康机型对 `0x101A` 的支持面未验证（竞品分析把它标在 ❓）→ **只读筛选先做，零协议风险**；写入另立小项，探测前不承诺。

- **实现状态（2026-09-24，只读半边落地）**：
  - 保护位从"解析出来就扔掉"变成一路带到实体：`CameraFile.protectionStatus: Int?`，两条来源各自填充——逐张 `0x1008`（结构里必有此字段，按 u16 取）与批量 `0x9805`（`0xDC03` 由解析器捕获，**没有退回逐张路径**，验收② 由 `MtpObjectPropListParserTest` 4 条钉住）。
  - **`null` ≠ 未保护**。这是本项唯一容易做错的地方：机身批量属性回哪几列随机型而定，若把"没报"当成"没保护"，「只传已保护的」会筛出空列表，用户看到的是"我明明按了保护键"。判定函数集中在 `camera/gallery/ProtectionFilter.kt`（非零即已保护，未报告单列一档 `UNREPORTED`），8 条单测。
  - 界面：闸门开着**也不**凭空长出一个标签——`protectChipOf()` 判机身确实报了保护列才 `VISIBLE`，且只在相机相册；标签带张数（`已保护 3`），与「已标记 N」同一读感。闸门关着时 `setupChips()` 连这个 TextView 都不创建，标签行与 v2.3.2 逐位一致。
  - 不做写入：全仓仍无 `0x101A`，UI 无任何"改机内状态"的动作（验收③）。
  - **待真机**：Z 系机身走 `0x9805` 时到底回不回 `0xDC03`——不回则这个标签永不出现（功能对这台机器等于不存在），回了则顺手可验「筛出的就是按过保护的几张」。已并入 §九 矩阵。

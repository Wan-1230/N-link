# 贡献指南与仓库内容规则

本文件是 N-Link 仓库的**强制性内容规范**。所有提交（commit）与推送（push）都必须符合本规范。

---

## 一、核心原则

> **仓库只描述 N-Link 自己的东西。**

仓库是对外公开分发的产物，读者只能看到这里的内容。因此：

**不允许**出现任何可识别第三方产品的信息 —— 无论以何种形式、何种措辞。

---

## 二、禁止入库的内容（红线）

以下内容**一律不得提交到远端仓库**：

| 类别 | 具体包括 |
|---|---|
| **横向评估** | 横向对比、对比矩阵、差距清单、优劣势对比、评分、"我们比 X 强/弱"类结论 |
| **产品规划中的同类产品视角** | 以"对照 X""向 X 学习""X 有而我们没有"为依据的需求条目与路线图 |
| **外部产品调研** | 对其他 App/软件/服务的功能调研、能力盘点、SDK 可得性调研 |
| **静态分析 / 实测取证** | 静态分析结果、静态分析/DEX/SO 分析、解包产物索引、偏移量与符号表摘录 |
| **外部产品标识信息** | 软件名称、包名（`com.xxx.yyy`）、应用 ID、内部代号、界面截图、图标 |
| **外部产品链接** | 对方官网、下载页、商店页、社区帖、issue 链接 |
| **打赏 / 变现相关调研** | 同类产品的定价、订阅、付费墙、权益设计调研 |

**违规示例**（均禁止）：

```markdown
某某App 在 STA 模式下采用进程级绑定。
四款同类产品的静态分析里都有 CloseSession。
横向评估显示我们在监看分辨率上落后一档。
某某 的录像链路走 0x9435(1) 进入应用模式。
```

**正确写法**：

```markdown
STA 链路采用进程级绑定（bindProcessToNetwork）。
拆链路前先发一次 CloseSession(0x1003)，各家现成实现普遍都这么做。
监看分辨率暂不支持按固件分支调整，记入待办。
录像链路：开录前 0x9435(1) 进入应用模式，收录后 0x9435(0) 退出。
```

## 三、允许入库的内容

以下**不受**本规范限制：

- **协议与标准事实**：PTP / PTP-IP / CIPA DC-005-2005 / USB / Android API 的公开规范与官方手册
- **平台官方文档**：Android Developer、Chrome、AOSP 等官方文档链接
- **本项目自身的技术决策**：为什么选 A 不选 B、实测标定值、踩坑记录、根因分析
- **本项目自身的实测数据**：真机日志、机身官方应用结果、性能指标
- **本项目自身的产品规划**：FR 条目、优先级、验收标准 —— 前提是**不引用外部产品作为论据**

判断标准：**这段话去掉所有外部产品信息后，剩下的是不是仍然成立的技术表述？**
如果是 → 改写后入库；如果不是 → 整条移除。

## 四、落地机制（三层防护）

### 第 1 层：`.gitignore` 排除

横向评估类文件**默认就不该出现在仓库里**。以下路径已被排除：

```gitignore
# ── 外部产品调研与横向评估（不入库，仅本地保留）──
/docs/横向评估*
/docs/同类产品*
/docs/对比*
/docs/*同类产品*
/docs/*对照*
/research/
/_apk_re/
/tools/apk-analysis/
/dist/
```

被排除的内容请放在上述路径下，它们只在本地存在，不会被推送。

### 第 2 层：提交前检查脚本

```bash
python tools/check_repo_hygiene.py
```

- **检查范围**：所有被 git 跟踪的 `.md` / `.kt` / `.xml` / `.kts` / `.py` 文件
- **检查内容**：产品名、包名、同类产品类措辞、静态分析痕迹
- **退出码**：`0` = 通过；`1` = 发现违规，阻止提交
- 建议挂到 `pre-commit` 钩子（见第 3 层）

首次配置：

```bash
python tools/install_hooks.py
```

### 第 3 层：git hooks（自动拦截）

`tools/install_hooks.py` 会安装 `.git/hooks/pre-commit`：

```
提交时自动运行 check_repo_hygiene.py
发现违规 → 拒绝提交，打印违规文件与行号
```

如需临时跳过（**不推荐**，且跳过记录会留在 reflog）：

```bash
git commit --no-verify
```

## 五、发现历史遗留怎么办

如果清理过程中又发现新的第三方表述：

1. **能改写的** → 改写为中立的技术描述（保留技术语义）
2. **整段都是同类产品内容的** → 删除整段，替换为占位说明：

   ```markdown
   > **本节内容已按仓库规则移除。**
   >
   > 依据 [`docs/CONTRIBUTING.md`](../../CONTRIBUTING.md)「外部产品信息不入库」一条，
   > 这类内容不得提交到远端仓库，故整节移除。
   ```

3. **不确定算不算的** → 按红线从严处理，拿不准就删

修改后务必重跑 `python tools/check_repo_hygiene.py` 确认。

## 六、提交说明（commit message）规范

提交说明同样受本规范约束：

- ✅ `fix(wifi-sta): STA 主机注册前先发 PrepareHost(0x952B)`
- ❌ `feat(connect): 对照某某的时序档`
- ❌ `docs: 同类产品复核第 3 次`

**不要**在提交说明里写外部产品名。写操作码、写模块、写问题现象。

---

## 七、例外机制

确实需要引用外部资料时，走以下流程，**不要在仓库内实现**：

1. 在**本地工作副本**（被 `.gitignore` 排除的路径）保留完整分析
2. 仓库内只写**去掉外部标识后的技术结论**
3. 需要溯源时，通过本文件记录的规则反查本地副本

---

## 八、违规处理

发现远端仓库已有违规内容时：

1. 先做只读排查，列出文件与位置
2. 确认清理范围（尤其涉及历史重写时，必须先确认）
3. 最小化改动，不影响已跑通的功能
4. 清理后重跑检查脚本确认零命中
5. 补一条提交说明，说明清理范围与依据
